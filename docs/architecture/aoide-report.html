What Aoide is

general

Two things wear the name. Aoide is the orchestration core — a shell-only, headless-capable app server for a machine and its agents: any agent with a shell is fully capable (no MCP required), and every terminal is a conductable, tracked session by default, so a central agent can speak into any other running session. AoideOS is the distribution built on that core — the NixOS flake that additionally ships the Quickshell desktop and the song/livery ricing engine. Aoide is the server; AoideOS is one venue it plays. You clone and run it, not install it.

The naming thesis in one line: architecture is frozen music — the Nix layer is the score, the running desktop is the performance, a rice is a song the system sings, and the host performing it is the venue.

The server framing is not a metaphor bolted on after the fact; the repo asserts it as a test any file can fail (CONTRACTS.md §0): delete every .qml in the repo — is this capability still reachable from a terminal? No means it is in the wrong place. One body, several doors.

§

Why Aoide

the thesis

A conventional desktop configuration is a fixed product. Its UI is the product — the bar, the theme, the launcher are the thing itself, so replacing any of them means surgery on the core: an import list edited, a config rewritten, a fork maintained. A conventional agent harness has the mirror problem: it owns a model loop but not a machine. Aoide inverts both. The harness is the product; every surface — the painted desktop included — is a client that mounts, and anything a client can do is reachable with only a shell.

the harness kernel a client the next client mounts here

Everything mounts, everything reverts. Capabilities enter the server by existing: lib/walk.nix discovers dendrites, facets, packages, and songs by walking the tree, so a new capability is a new folder — never an edit to an import list — and removing it leaves no trace. The doctrine has a temporal half too: every effect is revertible. Drafts route through a symlink, every draft write mints a take, rice back restores the live stage exactly, and beneath it all NixOS generations make the frozen half atomically reversible. The repo names its source — Cordis's spatial and temporal composability, adopted as CONTRACTS.md §0: when a design choice is open, take the one that can be deleted.

One protocol, structurally. The server's ingress cannot drift apart because there is nothing to drift: the CLI dispatcher, schema --json, the MCP tool list, and the A2A AgentCard all derive from one Registry in one crate, and nothing else in the tree enumerates commands. Adding a door is a façade; adding a capability is a registry entry every door advertises at once.

What this buys that neither parent can do. A conventional rice cannot hot-preview a different song's widgets without a rebuild; Aoide stages any committed song live, because all songs' QML ships at once and slots re-resolve on a songName change. A conventional rice cannot be driven safely by an agent; Aoide's write paths are gated — the rebuild is user-gated, graph send queues pending, an A2A spawn runs only the operator-configured command, and every door writes one audit log. A conventional harness cannot observe local agents for free; Aoide's conductor tracks every terminal mechanically — hooks, PTY, transcripts — because observing is free; conversing costs tokens. And the whole thing travels: a song is a host-agnostic score, any venue performs it by naming it, and the core is a flake that runs wherever Nix does.

That is the whole argument: the desktop is the first client Aoide ever serves — it is not the product. It is why every chart below draws Quickshell at the edge, never at the center.

I.

The protocol — one schema, N doors

ingress

Every capability is reachable through one command registry via three doors — the CLI (humans, scripts, the TUI), the MCP façade (an agent reaches for tools), and the A2A door (a peer agent speaks over the wire). All three derive from the same schema in the protocol crate, so they cannot drift; untrusted input stops in the server crate, which never depends on the trunk — the assembled registry is injected at launch.

The A2A door is complete and bidirectional (phases A–F all landed): AgentCard at /.well-known/agent-card.json, message/send (inject or spawn), tasks/get, SSE streaming, and the client side (a2a agent add/list/remove/send, folded into the session DAG as kind:"a2a" nodes). Peer federation rides the same door: another aoide registers as a peer (aoide peer add), aoide/graphSummary pulls its whole resolved session graph, and it folds in as a peer:* subtree — fresh within a 5-minute TTL, stale-but-present otherwise, never silently dropped.

Two planes, honestly. The command plane above is the one schema. There is a second, narrower contract — the state plane: song/stage/*.json documents the server publishes and clients watch, plus the shellbridge socket the painting client writes back through (CONTRACTS.md §4). It is versioned separately and is not registry-derived; the next section shows it as the server's notification stream.

Security model. The capability is admitted at rebuild time — enabling the door (aoide.a2a.enable, off by default, loopback by default) and setting aoide.a2a.spawnAgent are nix options, so turning A2A on goes through the normal rebuild gate, and a spawn only ever runs the configured command (the client supplies the prompt, never the argv). Per request there is now real gating too: a non-loopback message/send auto-delivers only from a peer explicitly marked autogate — anything else queues pending for a human (2026-08-14) — and with aoide.a2a.tokenFile set, a bearer token gates spawn and strips loopback's automatic trust, closing the reverse-proxy hole (2026-08-19). Every outcome audits through Door::A2a into the one log every door writes.
II.

The server at work

runtime · one request, traced

A real request, end to end — an A2A message/send steering a running session, chosen because it crosses every layer. The request path is solid; everything a client learns — envelopes, streams, published state — returns dashed. The painting client appears exactly once, at the edge, consuming the same published state any client could.

solid = request path · dashed = responses and published-state notifications · dotted = audit — the desktop appears only as a client, and policy sits off the paint path

client-side server-side process published document

The state plane is the notification stream. Producers — agent hooks (claude, kimi, pi via the AgentProfile seam), aoide conduct PTYs, the reaper, dunst — feed shellbridge.service, which is the single writer of song/stage/*.json. Notifications ride the same seam: dunst owns the freedesktop bus but draws nothing (skip_display on every rule) — each notification goes through aoide herald push into stage/herald.json, the QML herald only reads it, and a click returns through the socket (heraldverdict / heralddismiss). A permission summons carries real approve/deny buttons whose verdict routes back to graph send, the one gated injection door.

Truth vs sketch. aoide rice stage writes the live stage twin and best-effort hyprctl keywords — a sketch, no rebuild. The gated rebuild is the truth: it bakes the same aoide.livery into hyprland.conf and the Stylix fan-out, rsyncs the QML tree to run/qml/ (rsync -a --delete — a switch reasserts the store's truth over hot edits), and re-seeds the stage from the active song's committed livery, so a host that never staged anything still boots correct. Both fan-outs derive from one aoide.livery, so sketch and truth cannot drift.

The rice loop has mechanical rails now. Three modes (stage/mode.json): staging unlocks live writes, declarative refuses them (the safe default), and draft routes stage/livery.json through a symlink into a saved draft. Inside a draft, every write mints a take (a tree with parent pointers, not a line), rice take mark stamps reviewed states with a letter, and rice back restores any take or mark — snapshotting un-taken drift first, so nothing is ever destroyed. All live today.

III.

What it serves — songs, slots, the seam

livery · songbook

A song is a committed, host-agnostic score: it sets only aoide.livery (its dress) and aoide.arrangement (its structure) and never touches host options — the venue decides its instruments; the song carries only the notes. Every committed song's widget QML ships at once, so slots re-resolve live on a song switch, falling through the baseline chain: the active song, else sonata, else the anchor's own fallback, else nothing.

a declared slot with no body is inert, not an error · the venue decides its instruments — the song carries only the notes

live landed, unwired (bronze chip) dashed container = grouping · dashed leaf = extension point published document

The paint test decides where a QML file lives (CONTRACTS.md §0, mirrored in slots.md). A file stays in the facet only if all three are yes: it names zero aesthetic decisions; a second, unrelated song would use it unchanged; and its job is one of exactly three — publish state as data, resolve/host a song's QML, or be the entry point wiring one into the other. Any no, and it belongs in song/songbook/<song>/widgets/. The facet is not a component library.

The migration that test drives is mid-flight, honestly. P0 (the doctrine) and P1–P2 (GadgetFrame, BarPopout, AudioColonnade, MorphState, the stele popouts) landed reviewed-clean; sonata's songbook now carries the dock, wallpaper, and gadget bodies as staged twins. P3 — the facet switch — is the gate: it awaits the User's rebuild, and everything after it (deleting the dead facet bodies, the preview harnesses, the LiveryState grammar split) queues behind. Until then shell.qml still instantiates the facet-side bodies, which is what the bronze chip in the chart records.

Two registries, two questions. manifest.json answers "which slot bodies exist" (any lowercase widgets/*.qml a song drops; uppercase files are helper types, declared per-song in a generated qmldir). registry.json answers "which slots did a song declare as a widget type" via aoide.arrangement.widgets — surface kind (own layer-shell window, namespace, shortcut) hosted by SongSurfaces, dock kind (an item in the dock's gadget column) hosted by SongGadgets. etude proves the surface pipeline end to end; nocturne proves dock plus wholesale structural inheritance — it authors no bar at all and still gets sonata's, re-dressed in its own palette. rice lint validates the declarations strictly, native in crates/song/src/livery/ — the livery engine that replaced the old Node token package outright.

IV.

Where a harness attaches

ingress, from outside

Plate II traced one request inward. This is the same spine seen from the outside — every place an external coding harness, or anything else that wants to drive the machine, can attach: what it must speak there, what admits it, what gates it, and what comes back. Five attach points are live today. One — the cue — is designed and not built, and is drawn dashed for exactly that reason.

solid = the way in · dashed = what the harness gets back · dotted = the seam a new harness extends · the cue door is designed, not built

server-side process the protocol substrate published document dashed container = grouping · dashed leaf = not yet real

What a harness must speak: argv and one envelope. The floor is a shell. aoide schema --json enumerates all 83 commands with their args, flags, and gating; aoide guide is the prose companion. Every command answers in the same Outcome shape — status, command, message, gated, a changed list that is empty exactly when nothing happened (the idempotency signal), and an optional data payload (crates/protocol/src/output.rs). A harness that can run a subprocess and parse JSON is already a full client; the other doors add reach, never capability.

The hook attach point is not a fourth protocol. aoide hooks install claude|kimi|pi merges one entry into the harness's own settings file, and that entry runs aoide graph session hook — the CLI door, one registry verb, the harness's hook payload arriving on stdin (crates/conduct/src/commands/hooks.rs). The payload is treated as data and never propagates as a command. Teaching Aoide a new harness is therefore one entry in protocol::agents — its hook-event map, transcript locator, permission vocabulary, and context ceiling — after which the hook door, the transcript refresh, the window listener, and the reaper all dispatch through the table without a second edit.

What gates it, in two layers. The capability is admitted at rebuild time: aoide.a2a.enable is off by default and binds loopback, and aoide.a2a.spawnAgent names the only command a spawn may ever run, so a client supplies a prompt and never an argv. Per request, crates/server/src/a2a.rs resolves an origin (loopback vs. remote) and a bearer token; once aoide.a2a.tokenFile is set, loopback stops being a trust signal at all, which is what closed the reverse-proxy hole. Then, inside graph::send, a second and separate gate decides delivery: an explicit --yes, the box-wide AOIDE_CONDUCT_AUTOGATE, or the sender being the target session's parent — an orchestrator freely commanding a child it spawned. Anything else queues in stage/pending.json for a human. That gate applies to every door, not just A2A.

One honest limit on the wire door. The AgentCard advertises every implemented command as an A2A skill, but the door itself answers exactly five methods — message/send, tasks/get, aoide/graphSummary, and the two SSE methods (message/stream, tasks/resubscribe). Over the wire, A2A drives sessions: inject text into a known one, or spawn the configured agent. Arbitrary-verb dispatch is the CLI door (argv) and the MCP door (stdio) — both local. A remote harness that wants to call rice lint directly does not have a door for it today; it drives a local session that does.

The seam that makes the philosophical claim true. CONTRACTS.md §0 asserts it as a test, not a slogan: delete every .qml in the repo, and any capability still reachable from a terminal was in the right place. Because a harness attaches through the same doors the painting desktop uses — and the desktop's own return path is the shellbridge socket, one more client verb — an agent driving Aoide can reach the code that builds the OS and the code that builds the door it is speaking through. The seam is real; the limit is deliberate. Authoring the change is ungated; admitting it is not — the rebuild stays user-gated, so an agent can write its own harness and cannot switch the system onto it alone.

The chassis

Nix · build plane

The build plane provisions the server and its clients. nucleus holds the core services and the aoide.* option contract; dendrites are additive per-app integrations, each dormant until a host flips its .enable; facets are render surfaces reading only aoide.livery + aoide.arrangement. Everything is walker-discovered — modules/, pkgs/, and song/songbook/ alike — and the repo root is closed: new content lands inside the tree at its designated place, never as a new root entry. A host is a venue: it names its song in one line and decides its own instruments.

V.

The loop that builds it

process · as architecture

Aoide is built by the loop it exists to run — the harness dogfooding itself. The diff in "diff agent loop" is different: the agent that reviews is never the agent that wrote. The value is not a second opinion. It is that the second agent re-derives the first one's claims instead of confirming them — it re-runs the checks in its own worktree rather than reading the report and agreeing.

solid = the forward path · dashed = what comes back, including the coaching edge · dotted = consulted, off the chain · the loop's value is the re-derivation, not the second opinion

the orchestrator a dispatched agent evidence produced an advisor, off the chain dashed container = grouping · dashed leaf = extension point

Review is a coaching step, not a verdict slot. The clearest case is fugue, this repo's second song. A Sonnet wrote its bar and herald (82ba5f9); a different Sonnet reviewed and found the new song had reintroduced two bugs sonata had already fixed. bar.qml bound implicitWidth off parent.width while WidgetSlot binds its own width off the loaded item's implicitWidth — a loop that sonata's bar.qml documents and defuses by binding width directly. And herald.qml keyed its dismiss clock on notification id alone, so dunst's stack_duplicates id reuse latched a lapsed toast forever; sonata carries an arrivals/sameArrival re-arm check on receivedAt for exactly that. The executor defended the first as an intentional simplification. The reviewer went and read sonata's fix, rejected the defence on the evidence, and coached the executor straight to the change — agent to agent, not a verdict routed back through the orchestrator. That is 19ee9e4.

Re-derivation, not confirmation. A report is an assertion, and the loop's whole point is to make someone else earn it independently. In 8c087ba the executor's central claim was strong and unfalsifiable from the diff alone: sonata's new _widgets/ shelf changes nothing, because lib/walk.nix drops any /_ path and so the built Quickshell config derivation stays byte-identical, file for file, down to manifest.json and registry.json. The reviewer did not read that and agree. It reproduced the derivation-identity gate in its own worktrees and compared the outputs itself. A reviewer that only checks whether its own suggestions were applied has stopped reviewing; the standing rule is that it grades is this wrong, never did my change regress it.

Vocabulary is a review surface too. 1d1465f renamed a widget record's instruments field to packages: the lexicon reserves instruments for what a venue sounds — which facets and dendrites a host enables — so the field's name meant the wrong thing twice, and implied a song choosing its own facets, which CONTRACTS.md forbids outright. The follow-up (419628a) settled a second review flag in the same area: the guard's error message and the comment above it had hedged between two words, and an unsettled field name reads as an unsettled contract. Neither is a bug; both are the kind of drift only a second reader catches.

The orchestrator's own test. It concretizes the ask, dispatches one role per unit, tracks, and lands by pathspec — never git add -A, never a stash, because other sessions are committing into this same index concurrently. It does not execute and it does not review. The dividing line for small work is one question: does this need a whole agent? A typo, a margin, a one-line tweak, a config bump — those stay with the orchestrator, because a cold agent would spend more re-deriving the context than the edit is worth.

Where the manual lags practice. docs/Aoide-Wiki/protocol/AOIDE-DEV.md §2.1 is right about the shape — plan, execute, review; "review coaches the executor via SendMessage; it is not a bare pass/fail"; "the orchestrator dispatches and verifies, but does not implement or review" — but it is stale in two places. It assigns review to the flagship tier, where practice is a different mid-tier peer reviewing and the flagships sitting beside the chain as advisors: Fable on architecture and design, an Opus on code judgement. And it says the design advisor is on call only when the User asks for it, which no longer describes how the design passes have actually run. The requirement that the reviewer re-derive rather than accept the report is not written down anywhere yet. This chart is the current truth; the manual is the item to amend.

The web app — planned, not built

a fourth client · and one real gap

Nothing in this section exists. No crate, no route, no file. It is described here because the shape of the ask is architecturally interesting: a browser surface that streams agent processes, drafts, and derivations; logs system output including the diff verbs' output; possibly carries the settings panel; and lets commands be quickfired at the system — "a similar job to what the CLI does, but even more extensive." The claim worth testing is that this is another client of the same server, exactly like the CLI and the desktop, needing no new protocol. Half of that holds and half of it does not, and the honest half is the more useful one.

dashed = planned, nothing exists · solid = live today · dotted = the reach a live piece actually has · the bronze box is the gap, not a design

live — the protocol substrate live — a running surface live — published document planned — no code exists

The command half of the claim holds. Quickfiring a command from a browser needs no new protocol and no new vocabulary. There is one registry, one dispatcher, one Outcome envelope, and the report's own §I rule applies unchanged: adding a door is a façade; adding a capability is a registry entry. A web command door would be a fourth façade over dispatch() — the same shape mcp serve already is, differing only in transport. On this plane the web app really is another client of the same server, and the settings panel is the easiest case of all: settings are commands, and every one of the 83 already describes itself through schema --json.

The streaming half does not, and that is the finding. Everything the ask names as a stream — agent processes as they move, drafts as they mint, derivations as they build, system and diff output as it is produced — has no transport today. Three things come close and each falls short for a different reason, verified in the tree:

What existsWhat it actually carriesWhy it does not reach a browser
A2A SSEmessage/stream and tasks/resubscribe re-poll one task off the stage every 750 ms and emit only when its A2A state changes, closing on a terminal state or a 10-minute cap.It is a five-value state signal for one session — not output, not drafts, not build progress. Nothing streams bytes.
song/stage/*.jsonThe real notification stream: atomic documents (sessions, graph, herald, livery, mode, pending, projects, cover, hooks, …) that shellbridge.service is the single writer of.Clients consume it by watching files — that is how the Quickshell client works. A file watch does not cross a network, and no route serves these documents.
aoided event busThe neutral event stream with default-deny-per-class subscriptions — exactly the right model for this.It is a walking skeleton: real in-memory types, a demo loop, and no transport whatsoever. Nothing can subscribe from outside the process.

So the honest statement is a split one. The web app is a door consumer on the command plane and a protocol extension on the state plane. The report has said all along that there are two planes and that the second one — song/stage/*.json plus the shellbridge socket — is versioned separately and is not registry-derived. This is the first ask that lands squarely on that second plane, and it exposes what has been true and unremarked: the state plane has a publication mechanism but no subscription mechanism. Every existing consumer is a local process that can watch a file.

What that implies, stated as a gap and not as a design. A web app needs a way to subscribe to state-document changes and to process output over a socket — which is a new contract with its own versioning, its own authentication story (the A2A door's bearer and origin rules are per-request and one-shot; a long-lived stream is a different problem), and its own back-pressure and truncation semantics for output that a session can produce faster than a browser consumes. Three pieces of the substrate are already in the right shape to build on and none of them is the thing: shellbridge is a single writer that could publish as well as write; aoided's default-deny class model is the correct authorisation shape; and the A2A door proves the house can hold an HTTP connection open and stream to it. Deciding which of those becomes the transport is the first real question, and it has not been asked yet.

Read this section as a gap, not a plan. Nothing above is designed, locked, or scheduled — there is no wiki page, no phase list, and no code. Its value is the negative result: the tidy answer ("just another client, no new protocol") is half right, and the half that is wrong is the half that would have been discovered late. If this is built, the streaming contract is the thing to design first, because the command façade is a small, well-understood piece of work and the transport is not.
