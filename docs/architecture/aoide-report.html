What Aoide is

general

Two things wear the name. Aoide is the orchestration core — a shell-only, headless-capable app server for a machine and its agents: any agent with a shell is fully capable (no MCP required), and every terminal is a conductable, tracked session by default, so a central agent can speak into any other running session. AoideOS is the distribution built on that core — the NixOS flake that additionally ships the Quickshell desktop and the song/livery ricing engine. Aoide is the server; AoideOS is one venue it plays. You clone and run it, not install it.

The naming thesis in one line: architecture is frozen music — the Nix layer is the score, the running desktop is the performance, a rice is a song the system sings, and the host performing it is the venue.

The server framing is not a metaphor bolted on after the fact; the repo asserts it as a test any file can fail (CONTRACTS.md §0): delete every .qml in the repo — is this capability still reachable from a terminal? No means it is in the wrong place. One body, several doors.

Why Aoide

the thesis

A conventional desktop configuration is a fixed product. Its UI is the product — the bar, the theme, the launcher are the thing itself, so replacing any of them means surgery on the core: an import list edited, a config rewritten, a fork maintained. A conventional agent harness has the mirror problem: it owns a model loop but not a machine. Aoide inverts both. The harness is the product; every surface — the painted desktop included — is a client that mounts, and anything a client can do is reachable with only a shell.

the harness kernel a client the next client mounts here

Everything mounts, everything reverts. Capabilities enter the server by existing: lib/walk.nix discovers dendrites, facets, packages, and songs by walking the tree, so a new capability is a new folder — never an edit to an import list — and removing it leaves no trace. The doctrine has a temporal half too: every effect is revertible. Drafts route through a symlink, every draft write mints a take, rice back restores the live stage exactly, and beneath it all NixOS generations make the frozen half atomically reversible. The repo names its source — Cordis's spatial and temporal composability, adopted as CONTRACTS.md §0: when a design choice is open, take the one that can be deleted.

One protocol, structurally. The server's ingress cannot drift apart because there is nothing to drift: the CLI dispatcher, schema --json, the MCP tool list, and the A2A AgentCard all derive from one Registry in one crate, and nothing else in the tree enumerates commands. Adding a door is a façade; adding a capability is a registry entry every door advertises at once.

What this buys that neither parent can do. A conventional rice cannot hot-preview a different song's widgets without a rebuild; Aoide stages any committed song live, because all songs' QML ships at once and slots re-resolve on a songName change. A conventional rice cannot be driven safely by an agent; Aoide's write paths are gated — the rebuild is user-gated, graph send queues pending, an A2A spawn runs only the operator-configured command, and every door writes one audit log. A conventional harness cannot observe local agents for free; Aoide's conductor tracks every terminal mechanically — hooks, PTY, transcripts — because observing is free; conversing costs tokens. And the whole thing travels: a song is a host-agnostic score, any venue performs it by naming it, and the core is a flake that runs wherever Nix does.

That is the whole argument: the desktop is the first client Aoide ever serves — it is not the product. It is why every chart below draws Quickshell at the edge, never at the center.

The A2A door is complete and bidirectional (phases A–F all landed): AgentCard at /.well-known/agent-card.json, message/send (inject or spawn), tasks/get, SSE streaming, and the client side (a2a agent add/list/remove/send, folded into the session DAG as kind:"a2a" nodes). Peer federation rides the same door: another aoide registers as a peer (aoide peer add), aoide/graphSummary pulls its whole resolved session graph, and it folds in as a peer:* subtree — fresh within a 5-minute TTL, stale-but-present otherwise, never silently dropped. Federation is live-proven, and two-way on two edges — sakaki called this door over an ssh tunnel on 2026-08-20, and by 2026-08-21 both yomi↔sakaki and yomi↔osaka ran in both directions: cards fetched each way, aoide/graphSummary returning each instance's own identity rather than an echo of the caller's, and message/send landing in a real conducted session at the far end (see §V).

Two planes, honestly. The command plane above is the one schema. There is a second, narrower contract — the state plane: song/stage/*.json documents the server publishes and clients watch, plus the shellbridge socket the painting client writes back through (CONTRACTS.md §4). It is versioned separately and is not registry-derived; the next section shows it as the server's notification stream.

Security model. The capability is admitted at rebuild time — enabling the door (aoide.a2a.enable, off by default, loopback by default) and setting aoide.a2a.spawnAgent are nix options, so turning A2A on goes through the normal rebuild gate, and a spawn only ever runs the configured command (the client supplies the prompt, never the argv). Per request there is now real gating too: a non-loopback message/send auto-delivers only from a peer explicitly marked autogate — anything else queues pending for a human (2026-08-14) — and with aoide.a2a.tokenFile set, a bearer token gates spawn and strips loopback's automatic trust, closing the reverse-proxy hole (2026-08-19), and the same predicate now gates every read verb too (Phase G, 2026-08-20). Every outcome audits through Door::A2a into the one log every door writes. §V draws the whole trust model outside-in — network posture, peer enrolment, this door, and the local gate — with the open edges named.

The state plane is the notification stream. Producers — agent hooks (claude, kimi, pi via the AgentProfile seam), aoide conduct PTYs, the reaper, dunst — feed shellbridge.service, which is the single writer of song/stage/*.json. Notifications ride the same seam: dunst owns the freedesktop bus but draws nothing (skip_display on every rule) — each notification goes through aoide herald push into stage/herald.json, the QML herald only reads it, and a click returns through the socket (heraldverdict / heralddismiss). A permission summons carries real approve/deny buttons whose verdict routes back to graph send, the one gated injection door.

Truth vs sketch. aoide rice stage writes the live stage twin and best-effort hyprctl keywords — a sketch, no rebuild. The gated rebuild is the truth: it bakes the same aoide.livery into hyprland.conf and the Stylix fan-out, rsyncs the QML tree to run/qml/ (rsync -a --delete — a switch reasserts the store's truth over hot edits), and re-seeds the stage from the active song's committed livery, so a host that never staged anything still boots correct. Both fan-outs derive from one aoide.livery, so sketch and truth cannot drift.

The rice loop has mechanical rails now. Three modes (stage/mode.json): staging unlocks live writes, declarative refuses them (the safe default), and draft routes stage/livery.json through a symlink into a saved draft. Inside a draft, every write mints a take (a tree with parent pointers, not a line), rice take mark stamps reviewed states with a letter, and rice back restores any take or mark — snapshotting un-taken drift first, so nothing is ever destroyed. All live today.

III.

What it serves — songs, slots, the seam

livery · songbook

A song is a committed, host-agnostic score: it sets only aoide.livery (its dress) and aoide.arrangement (its structure) and never touches host options — the venue decides its instruments; the song carries only the notes. Every committed song's widget QML ships at once, so slots re-resolve live on a song switch, falling through the baseline chain: the active song, else sonata, else the anchor's own fallback, else nothing.

a declared slot with no body is inert, not an error · the venue decides its instruments — the song carries only the notes

The paint test decides where a QML file lives (CONTRACTS.md §0, mirrored in slots.md). A file stays in the facet only if all three are yes: it names zero aesthetic decisions; a second, unrelated song would use it unchanged; and its job is one of exactly three — publish state as data, resolve/host a song's QML, or be the entry point wiring one into the other. Any no, and it belongs in song/songbook/<song>/widgets/. The facet is not a component library.

The migration that test drives is mid-flight, honestly. P0 (the doctrine) and P1–P2 (GadgetFrame, BarPopout, AudioColonnade, MorphState, the stele popouts) landed reviewed-clean; sonata's songbook now carries the dock, wallpaper, and gadget bodies as staged twins. P3 — the facet switch — is the gate: it awaits the User's rebuild, and everything after it (deleting the dead facet bodies, the preview harnesses, the LiveryState grammar split) queues behind. Until then shell.qml still instantiates the facet-side bodies, which is what the bronze chip in the chart records.

Two registries, two questions. manifest.json answers "which slot bodies exist" (any lowercase widgets/*.qml a song drops; uppercase files are helper types, declared per-song in a generated qmldir). registry.json answers "which slots did a song declare as a widget type" via aoide.arrangement.widgets — surface kind (own layer-shell window, namespace, shortcut) hosted by SongSurfaces, dock kind (an item in the dock's gadget column) hosted by SongGadgets. etude proves the surface pipeline end to end; nocturne proves dock plus wholesale structural inheritance — it authors no bar at all and still gets sonata's, re-dressed in its own palette. rice lint validates the declarations strictly, native in crates/song/src/livery/ — the livery engine that replaced the old Node token package outright.

Where a harness attaches

ingress, from outside

Plate II traced one request inward. This is the same spine seen from the outside — every place an external coding harness, or anything else that wants to drive the machine, can attach: what it must speak there, what admits it, what gates it, and what comes back. Five attach points are live today. One — the cue — is designed and not built, and is drawn dashed for exactly that reason.

What a harness must speak: argv and one envelope. The floor is a shell. aoide schema --json enumerates all 83 commands with their args, flags, and gating; aoide guide is the prose companion. Every command answers in the same Outcome shape — status, command, message, gated, a changed list that is empty exactly when nothing happened (the idempotency signal), and an optional data payload (crates/protocol/src/output.rs). A harness that can run a subprocess and parse JSON is already a full client; the other doors add reach, never capability.

The hook attach point is not a fourth protocol. aoide hooks install claude|kimi|pi merges one entry into the harness's own settings file, and that entry runs aoide graph session hook — the CLI door, one registry verb, the harness's hook payload arriving on stdin (crates/conduct/src/commands/hooks.rs). The payload is treated as data and never propagates as a command. Teaching Aoide a new harness is therefore one entry in protocol::agents — its hook-event map, transcript locator, permission vocabulary, and context ceiling — after which the hook door, the transcript refresh, the window listener, and the reaper all dispatch through the table without a second edit. §VI takes that claim apart seam by seam, with the live capability matrix for the three harnesses actually tried.

What gates it, in two layers. The capability is admitted at rebuild time: aoide.a2a.enable is off by default and binds loopback, and aoide.a2a.spawnAgent names the only command a spawn may ever run, so a client supplies a prompt and never an argv. Per request, crates/server/src/a2a.rs resolves an origin (loopback vs. remote) and a bearer token; once aoide.a2a.tokenFile is set, loopback stops being a trust signal at all, which is what closed the reverse-proxy hole. Then, inside graph::send, a second and separate gate decides delivery: an explicit --yes, the box-wide AOIDE_CONDUCT_AUTOGATE, or the sender being the target session's parent — an orchestrator freely commanding a child it spawned. Anything else queues in stage/pending.json for a human. That gate applies to every door, not just A2A.

One honest limit on the wire door. The AgentCard advertises every implemented command as an A2A skill, but the door itself answers exactly five methods — message/send, tasks/get, aoide/graphSummary, and the two SSE methods (message/stream, tasks/resubscribe). Over the wire, A2A drives sessions: inject text into a known one, or spawn the configured agent. Arbitrary-verb dispatch is the CLI door (argv) and the MCP door (stdio) — both local. A remote harness that wants to call rice lint directly does not have a door for it today; it drives a local session that does.

The seam that makes the philosophical claim true. CONTRACTS.md §0 asserts it as a test, not a slogan: delete every .qml in the repo, and any capability still reachable from a terminal was in the right place. Because a harness attaches through the same doors the painting desktop uses — and the desktop's own return path is the shellbridge socket, one more client verb — an agent driving Aoide can reach the code that builds the OS and the code that builds the door it is speaking through. The seam is real; the limit is deliberate. Authoring the change is ungated; admitting it is not — the rebuild stays user-gated, so an agent can write its own harness and cannot switch the system onto it alone.

V.

The trust layers

security · outside-in

Security here is not one gate but four layers, each answering a different question — who can reach the port, which peer is calling, what an unauthenticated caller may learn, and what may finally become a keystroke in a running session. The layers are read outside-in, the way a request arrives. L2, L3, and L4 are live on the running system; L1 is policy — an invariant plus the transport this box happens to borrow — and it has now been exercised once, over an ssh reverse tunnel, by a real remote peer. What is deliberately absent is listed as plainly as what is present.

solid = running today · dashed = a transport choice not made on this box, or a mechanism absent by design · line-boxed = a stated invariant · the rail is one request, read outside-in

live gate or mechanism published document not configured here — a swap, or absent by design a stated invariant — no code owed

L1 is an invariant with a default, not a product choice. The rule is borrowed encrypted transport, never server-side TLS: the door is a hand-rolled HTTP server, so encryption and machine identity are supplied by a layer beneath it and never implemented inside it. That is also why mTLS is rejected — client certificates would mean adopting a TLS stack the house has no other use for, or hand-rolling the hard half of a security protocol. The default binding is a tailnet (tailscale serve, with a WireGuard node key naming the machine rather than an address), but the invariant does not name a vendor: ssh -L, headscale, vanilla WireGuard, or a TLS-terminating reverse proxy in front of loopback are equivalent substitutions, and swapping one for another changes nothing above this layer. What stays forbidden either way is the door listening on a raw LAN or WAN address by itself. None of this is a running service today — the door is off by default and binds loopback — so L1 is drawn as policy, which is what it is. It has been exercised exactly once, and by one of the listed substitutions: the sakaki federation proof below borrowed a reverse ssh tunnel, and the door bound nothing but loopback for the whole of it.

L2 — enrolment is manual, and that is the whole feature. A peer joins by a human running aoide peer add <name> <url> --token-file <path>, which verifies the peer before it is written into state/peers.json; the file is an allowlist, and a caller that is not in it is a stranger. Each peer carries its own secret (root-owned, 0600) rather than sharing one, because a shared token cannot tell two peers apart. There is no mDNS, no discovery protocol, and no invite verb — at a fleet of roughly three machines, discovery would be more moving parts than the thing it discovers, and every one of those parts is a surface.

L3 — the door asks one question. token_authorized(token_configured, token_state) is the single predicate, and every arm of the door now asks it — the card GET, spawn (gated first, 23f0a0e) and every read verb — tasks/get, aoide/graphSummary, and both SSE methods — which returned an unauthenticated caller the operator's whole resolved session graph until Phase G closed it (6d2f38e, tests in 46296eb). The gate is computed in the dispatcher before the read runs, so a real session id returns the error rather than its state, and the SSE pair is gated at the top of stream_task so an unauthenticated stream neither injects nor spawns. With no token configured — today's default — every path is byte-identical to before, pinned by its own test.

The two edges that were open when this section was first drawn are now closed, and switched onto the live system. The AgentCard used to be served in full to any unauthenticated GET, advertising the whole implemented command inventory; 4e25fa3 serves a stripped card of exactly name, protocolVersion, and url instead, picked off the full card so the two cannot drift. It stays 200 in both arms and keeps the a2a.agent-card audit label — a GET returns a card, not JSON-RPC, so there is no -32005 here — and a valid bearer still gets everything. And an unauthenticated message/send naming a context id used to distinguish a real session from a bogus one and could write into the approval queue; cea9f1f answers it with a uniform synthetic submitted Task — the same shape for a real id, a bogus id, and a non-conductable one, with no session lookup and no queue write at all. The spawn arm keeps its -32005. Both landed with the no-token path pinned byte-identical, both went out in generation l9ghb2d (2026-08-20), and both were re-probed against the installed binary rather than a scratch build. What remains open at this layer is the rest of the #47 ladder, and it is named rather than implied: audit identity (F), the outbound bearer header (H), and auth-required-stays-local with the sudo-inject guard (K).

Why #50 shipped as a uniform response and not a hard gate. The obvious fix — refuse unauthenticated message/send outright — would have broken the peers the design exists for. An enrolled peer authenticates with its own per-peer token, not the server-wide one, and aoide's own outbound client sends no Authorization header at all today. A hard gate keyed on the server-wide token would therefore have rejected correctly-enrolled peers while closing a leak the uniform answer closes just as completely: no existence oracle, and no queue write from an unauthenticated caller. The outbound bearer header remains a tracked gap (#47 H).

The nuance that exemption carries, now stated in the contract (851c92d): a caller matched as an autogated peer by its per-peer token, while a server-wide token is configured and it presents no valid bearer for that, is exempt from the uniform arm and reaches the real inject machinery — but effective_origin still coerces it to Unknown (the 2026-08-19 behaviour), so it lands held pending in the approval queue rather than delivering. Fail-safe, and distinct from the synthetic arm, which never queues at all. That nuance had been living in a test comment.

All four layers, exercised at once — the sakaki proof (2026-08-20). Federation stopped being a local round-trip: a second machine — sakaki, Melete's box — called this door for real, and it did so over the borrowed-transport tier itself, a reverse ssh tunnel onto the loopback-only server, which never bound a routable interface at any point in the exercise. Every L3 answer held from off-box. The unauthenticated card GET returned exactly name, protocolVersion, and url; the same GET with a bearer returned the full card. message/send against a bogus context id with no token returned the uniform synthetic submitted Task — the existence oracle stayed closed to a stranger on a real network path — while the same call with a valid token returned an honest -32001, which is the point of the uniform arm: authenticated callers get true semantics, strangers get one shape. tasks/get unauthenticated returned -32005. And a real delivery landed in the target session's log as from dainty-dune (…8331): … — the petname mint and the terse provenance prefix, on a genuine cross-host inbound rather than a loopback rehearsal. This also stands as the Melete-inbound proof (#16).

Both directions, on both edges (2026-08-21). The August 20 run proved one direction into this box. Federation is now two-way on two edges — yomi↔sakaki and yomi↔osaka — each side enrolled as the other's peer, each edge riding an ssh tunnel. Cards were fetched in both directions; aoide/graphSummary returned each instance's own resolved graph and identity rather than a mirror of the caller's, which is the answer that distinguishes a real federated pull from a loopback rehearsal talking to itself; and message/send delivered into a genuinely conducted session at the far end, both ways. The doors on the far ends are the resident ones described in the venue section — sakaki headless, osaka beside its own desktop — so the federation edges are between always-on servers, not between two terminals that happened to be open.

A remote peer necessarily presents as loopback, and that is the design rather than a hole in it. Because L1's invariant is borrowed encrypted transport and never server-side TLS, a peer that is elsewhere arrives through a tunnel and reaches the door from 127.0.0.1: the origin address carries no information at this layer, and the door is not built to ask it for any. So the ladder reads exactly as written — a valid per-peer token on a loopback-presenting connection delivers immediately, and the held-pending path is reached through per-peer autogate policy, never through a raw remote IP the door will never see. Distrusting loopback here would distrust the only address a federated peer can ever have.

L4 — and the honest admission underneath all of it. The same-user control socket is the real authority boundary: anything on the box running as the User can open it, so no amount of door gating changes what a local process may do. That is why AOIDE_SESSION_ID is documented as attribution, not security — it is a same-user environment variable any caller can set, and the provenance prefix built from it says who claims to be sending, never who is authorised to. Delivery is decided by a ladder that does not consult it: an explicit --yes, the box-wide AOIDE_CONDUCT_AUTOGATE, the sender being the target's parent, siblings under one live parent (on by default per the User's 2026-08-20 call), and otherwise the pending queue with a human's approve/deny. All of that is live. The prefix is single-line and CR/LF-sanitized so an injected payload cannot manufacture a second line, and a bare permission-verdict keystroke is excluded from prefixing entirely — prefixing the digit a TUI is waiting to read would corrupt the answer.

What is deliberately absent, and why. No hand-rolled crypto — the only comparison the door does on a secret is a length-independent byte loop, and everything stronger is delegated to whatever transport L1 borrows rather than written here. No local name encryption — a session's petname, cwd, and title live in same-user files on a machine whose owner is the only user; encrypting them would protect nothing from an attacker who has already lost the L4 boundary. No discovery protocol, as above. Each of these is a decision with a reason, not a gap someone forgot.

VI.

Where a coding harness plugs in

five seams · one row each

Plate IV showed the doors an external caller speaks through. This is the narrower, more practical question: what does it cost to teach Aoide a coding harness it has never seen? Claude Code, kimi, pi, Codex, a DeepSeek harness — anything with a TTY or a CLI. There are five seams and all five are landed; the answer the architecture gives is that a new harness costs one AgentProfile row and no Rust beyond it, because injection is gated by conduction — a pty aoide owns — and never by the harness inside it.

solid = landed and in use · dashed leaf = the extension point, not a missing piece · the substrate is one pty, which is the whole argument

a landed seam the harness — outside aoide entirely the conducted substrate where the next harness lands

The profile table is the only per-harness registration point, and it is kept deliberately thin. protocol::agents holds one AgentProfile per harness: the hook-event map, the permission vocabulary, the sub-agent tool names, the payload normalizer, the model-context ceilings, the transcript locator and its extractors, the hook-settings spec, and permission_keys — the prompt hotkeys, verified by reading the live prompt on screen, or None, in which case the herald refuses to raise a summons rather than type a guess into someone's session. A field is added when live evidence earns it and not before, and the newest one shows the discipline working: submit_key landed (b6cbd03) because a live kimi proved that --submit's hard-coded \n typed a line without sending it. The keystroke is resolved from the target session's own profile at delivery time, never memoized when a send is queued, so a held entry approved later still speaks the right byte. There is still no spawn recipe, no capability matrix, and no tier map, because nothing consumes them.

The other four seams are all mechanism, not vocabulary. graph wrap --agent <name> -- <cmd> runs any CLI as a registered session; graph spawn is the detached headless form, re-execing conduct --headless into its own session with a per-session log at state/sessions/<id>.log and registration proven by a live socket connect. The hook door is the inversion of the other three: a harness session running inside a conducted terminal registers itself as a child by piping its own hook payload into aoide graph session hook — no new protocol, one registry verb, the payload treated as data. And graph send plus the pending queue types into the pty and holds what is not authorised for a human. None of the last four knows what harness it is driving.

Adding Aoide to the flake changed a non-participating host by exactly nothing.

A box that never paints had to be earned, in three fixes. The desktop had been hiding three assumptions, and each one showed up as the doors dying on a headless host rather than as a build error. One: the whole of shellbridge.nix is graphical-session machinery, but it was gated on bare aoide.enable, so a headless host shipped inert units whose PATH entries dragged quickshell, hyprland, and hyprlock into its closure; the module now gates on aoide.enable && aoide.facets.quickshell.enable, and a probe of an enable+a2a closure contains zero of those derivations (ccef9bb). Two: aoided was wantedBy/after/partOf graphical-session.target unconditionally — a target that never activates on a box with no session, so PartOf stopped even a hand-started daemon and BindsTo took the A2A and MCP doors down with it. It now anchors on the quickshell facet: painting hosts keep the exact graphical-session wiring (yomi-strix's toplevel derivation byte-identical), and facet-off hosts get default.target with no after/partOf, so with linger the daemon and its doors come up at boot and stay (2d5713b). Three, and the subtlest: aoided's binary runs its policy self-check, prints its status JSON, and exits 0 in about 25ms, because daemon::run has no event loop yet — and the unit declared Type=simple, so systemd read that clean exit as the service ending and BindsTo dropped the doors in the same second. The unit is now Type=oneshot + RemainAfterExit=true, which states what the binary actually does today and holds it active (exited) so the doors anchored to it stay resident; it reverts to simple the day the daemon grows a real loop (7fa52c8). A skeleton advertised honestly is a working anchor; a skeleton advertised as a daemon is an outage.

One collision, and one rejected shortcut. The collision was real: dxflake's ungated neovim dendrite pins its own rose-pine nvf theme, and Stylix — which arrives with the desktop facet — fights it over programs.nvf.settings.vim.theme.name. It is settled per-host with stylix.targets.nvf.enable = false, never repo-wide, so no host inherits a truce it was never party to. The shortcut, explicitly rejected: shelving dxflake's shared dendrites with a _ prefix to get them out of Aoide's way. Shelving is walk-global — it would have stripped those dendrites from hosts that have nothing to do with this integration and that still run them. A host-scoped problem does not get a repo-scoped fix.

The loop that builds it

process · as architecture

Aoide is built by the loop it exists to run — the harness dogfooding itself. The diff in "diff agent loop" is different: the agent that reviews is never the agent that wrote. The value is not a second opinion. It is that the second agent re-derives the first one's claims instead of confirming them — it re-runs the checks in its own worktree rather than reading the report and agreeing.

solid = the forward path · dashed = what comes back, including the coaching edge · dotted = consulted, off the chain · the loop's value is the re-derivation, not the second opinion

the orchestrator a dispatched agent evidence produced an advisor, off the chain dashed container = grouping · dashed leaf = extension point

Review is a coaching step, not a verdict slot. The clearest case is fugue, this repo's second song. An execute-tier agent wrote its bar and herald (82ba5f9); a different agent of the same tier reviewed and found the new song had reintroduced two bugs sonata had already fixed. bar.qml bound implicitWidth off parent.width while WidgetSlot binds its own width off the loaded item's implicitWidth — a loop that sonata's bar.qml documents and defuses by binding width directly. And herald.qml keyed its dismiss clock on notification id alone, so dunst's stack_duplicates id reuse latched a lapsed toast forever; sonata carries an arrivals/sameArrival re-arm check on receivedAt for exactly that. The executor defended the first as an intentional simplification. The reviewer went and read sonata's fix, rejected the defence on the evidence, and coached the executor straight to the change — agent to agent, not a verdict routed back through the orchestrator. That is 19ee9e4.

Re-derivation, not confirmation. A report is an assertion, and the loop's whole point is to make someone else earn it independently. In 8c087ba the executor's central claim was strong and unfalsifiable from the diff alone: sonata's new _widgets/ shelf changes nothing, because lib/walk.nix drops any /_ path and so the built Quickshell config derivation stays byte-identical, file for file, down to manifest.json and registry.json. The reviewer did not read that and agree. It reproduced the derivation-identity gate in its own worktrees and compared the outputs itself. A reviewer that only checks whether its own suggestions were applied has stopped reviewing; the standing rule is that it grades is this wrong, never did my change regress it.

Vocabulary is a review surface too. 1d1465f renamed a widget record's instruments field to packages: the lexicon reserves instruments for what a venue sounds — which facets and dendrites a host enables — so the field's name meant the wrong thing twice, and implied a song choosing its own facets, which CONTRACTS.md forbids outright. The follow-up (419628a) settled a second review flag in the same area: the guard's error message and the comment above it had hedged between two words, and an unsettled field name reads as an unsettled contract. Neither is a bug; both are the kind of drift only a second reader catches.

The orchestrator's own test. It concretizes the ask, dispatches one role per unit, tracks, and lands by pathspec — never git add -A, never a stash, because other sessions are committing into this same index concurrently. It does not execute and it does not review. The dividing line for small work is one question: does this need a whole agent? A typo, a margin, a one-line tweak, a config bump — those stay with the orchestrator, because a cold agent would spend more re-deriving the context than the edit is worth.

Where the manual lags practice. docs/Aoide-Wiki/protocol/AOIDE-DEV.md §2.1 is right about the shape — plan, execute, review; "review coaches the executor via SendMessage; it is not a bare pass/fail"; "the orchestrator dispatches and verifies, but does not implement or review" — but it is stale in two places. It assigns review to the flagship tier, where practice has settled into a three-way split (standing as of 2026-08-21): the architect tier plans the loops and advises — architecture, phase plans, sequencing, never the baton; the design tier owns front-end design passes — report pages, web surfaces, widget treatments; and the execute tier both executes and reviews, a different agent each time, never the author's own context. And the manual says the design advisor is on call only when the User asks for it, which no longer describes how the design passes have actually run. The requirement that the reviewer re-derive rather than accept the report is not written down anywhere yet. This chart is the current truth; the manual is the item to amend.

The same loop, unbound from the harness

tiers · bindings · one spec

Plate VII is the loop as it is run here — inside one harness that happens to have sub-agents. This is the same loop stated so it survives the harness: a tier is one fresh-context execution unit per role, and the mechanism that provides that unit is a binding, not a rank. There are two bindings and neither is above the other. Everything on this plate is a spec, not a verb — the primitives it composes are landed, and the loop itself lives as a wiki concept page (concepts/orchestration/Loop-Protocol.md), folding into the onboarding skill that is still queued.

solid accent = a fresh-context unit and the binding that is always available · bronze = the degraded rung and the judgment call · dashed here means deliberately absent, not pending

a role with its own context a binding — an optimization, not a rank the verb that will never exist

Why define the tier by context rather than by mechanism. Stated as "use sub-agents," the loop is a claim about one harness and evaporates the moment the orchestrator is kimi, or pi, or something not written yet. Stated as one fresh context per role, it is a claim about the work: the reviewer must not inherit the executor's reasoning, and the executor must not inherit the planner's rationalizations. Both bindings satisfy that. Sub-agents are an optimization within the rung — cheaper to start, invisible to anyone but the orchestrator — and graph spawn is the floor, because it works on any conducted harness at all. That is what makes "the default is tiered" a rule rather than a per-harness declaration: R1 is always reachable.

Three things force the session binding regardless of what the harness offers. A role that must run on a different harness or model than the orchestrator; a long-running executor that may need steering mid-flight; and any work the User should be able to watch. A spawned session has a log, a graph node, and a herald presence; an internal sub-agent has none of those, and it dies with the context that started it. Everything else is a per-brief judgment, with the standing guidance being the User's own: long-running executors get sessions, short scoped work gets internal sub-agents.

Model-tiering is seasoning, not the tier. Planning on a flagship and executing on a mid-tier is worth doing where the harness offers models, but it is orthogonal — fresh-context-per-role is a real tier on a single-model harness. What is not optional is review integrity: the reviewer never shares the executor's context on any rung, a distinct model or harness is preferred whenever one is on offer, and every reviewer brief carries the grading discipline in words — grade "is this wrong", never "did my change regress it". Same-model rationalization is a briefing failure, not a spawning one, and this repo has the scar to prove which of the two it was.

And the loop deliberately never becomes a verb. Every consequential step in it — ship or send back, coach or re-dispatch, kill an agent that has gone wide — is judgment. A graph loop command would freeze that judgment into Rust, where it would go stale on the first run that did not match the shape its author imagined, and where changing it would cost a rebuild. So the roles, the gates, the send-back cycle, and the degradation ladder live as a specification — Loop-Protocol.md in the wiki, to be folded into the installable onboarding skill once that lands, and defined in aoide's own verbs rather than any harness's tool vocabulary — while the code contributes only what it already has: spawn, send, the pending queue, view, logs, transcripts.

The one profile change this earned — and it is done. Nothing about the loop belongs in AgentProfile: no capability matrix, no tier map, no models list, no spawn recipe, because nothing would consume them. Exactly two edges of the substrate were still claude-shaped and both have landed — a per-profile submit_key consumed by graph send --submit and resolved at delivery time (b6cbd03), and kimi's permission_keys filled from a live screen rather than a guess (aedca0c). With the spec written down (4ab3fe6), #52 is closed. pi still gets no rung on the ladder until it completes a headless turn on the record.

Why two binaries and not a feature flag. A headless box that answers the A2A door should not carry a Qt and Wayland closure to do it — sakaki's whole Aoide duty is one door, and the venue section above records what the desktop's assumptions cost it. A build-time feature would shrink the closure and leave a worse problem behind: one schema still describing commands half the hosts cannot run, which makes schema --json — the published contract every door derives from — a document that lies on some machines. Two binaries means two honest schemas. It is also the same doctrine the rest of the report runs on: when a design choice is open, take the one that can be deleted, and a binary a host never installs is the cleanest deletion there is.

The conductor stays core, and that is the load-bearing call. It is the surface a headless box needs most — the roster, the pending queue, the log tail §V's headless work built — and it is pure Rust with no system-closure weight. More to the point, conducting is what Aoide is: the orchestration of agents is the identity, and the painting is the venue. A split that shipped the conductor with the paint binary would have named the wrong half as the core.

The exceptions are recorded as exceptions. shellbridge.rs and herald.rs are entangled with core in both directions — permit.rs publishes a summons through the herald, and the conductor reads the socket path the shellbridge owns — and they carry no dependency weight at all, so the files stay in conduct and only their registry lines move to lyra. storage::takes and storage::mode stay for the same shape of reason. Four smudges, written into PACKAGE-LAYOUT.md as smudges rather than quietly tidied, because an undocumented exception reads as a mistake to the next agent that finds it.

The schema becomes per-binary, and that is not a version bump. aoide schema --json becomes the core contract (48 commands) and lyra schema --json the AoideOS-surface contract (42 — one more than first estimated, because mcp serve must be a registered path in any binary whose parser routes it); a consumer that wants the whole desktop's inventory reads both. schemaVersion stays "0" because §3 has never promised a fixed command inventory — only a document shape, and the shape does not change. What moves is which binary emits an entry, never the entry's own structure. The AgentCard shrinks with it, which is wire-visible and will be said so in the commit that does it: the card advertises skills, and advertisement is all it has ever been.

The Cordis correspondence, stated so nobody re-litigates it. In the vocabulary CONTRACTS.md §0 already cites: a crate is a package — a plugin; an app crate (cli today, lyra after the split) is a dsh-style bundle, the ordered composition performed at boot; and the assembled Registry is the plugin tree. So an app crate's explicit register() list is the bundle's profile, not a violation of "no registry an author must edit to be seen" — composing a bundle at its root is how Cordis composes too. Riding with the same phase is a repo-structure convention borrowed from the same source: every plugin directory gets its own README.md (what this plugin is, its named seams, how it composes) and AGENTS.md (the invariants an agent must hold here, the extension points, what requires a docs update), layered so each level's file holds only that level's invariants, with CLAUDE.md symlinking AGENTS.md at each level. That convention absorbs the per-directory-docs item this report has carried as planned since the restructure.

And the hard constraint the whole split exists to make true: core is nix-independent. aoide, aoided, and the vault broker of §XI must build with cargo and run on any Linux — no nix shell-outs, no NixOS assumption, configuration through env and files, and systemd as packaging rather than a requirement. Only lyra may be nix-dependent, which is why song's nix eval call travels with it. The check is mechanical rather than aspirational: after the graphical paths leave core, the core tree must grep clean of nix invocations, and that grep is a gate on the phase.

Messaging and presence

planned · queued behind the split

§V made a second machine reachable. It did not make it legible: there is no way to ask which boxes are up, no way to name a session without pasting an id, and nothing durable holding a message that arrived while an agent was not looking. Planned, approved, serialized behind the split — every phase here appends to the registry the split rewrites, which is why it waits. Nothing in this section is built.

Presence is a live probe, not a cached guess — because the doors are resident now. That is the design decision the venue section earned: sakaki and osaka answer their doors whenever the box is up, so host-up equals door-answering, and a freshness-decayed cache would be modelling a problem that no longer exists. aoide who therefore probes every registered peer on every invocation, in parallel, with a short per-peer timeout, and the peer cache becomes only the fallback: an unreachable box shows as unreachable with its last-known sessions labeled as of their fetch time, never silently presented as current. There is no background pull timer in the design — the live probe replaces it. A node reads online, unreachable, or never-pulled; a session reads from the same vocabulary the graph already publishes, and a remote session from a live reply is exactly as trustworthy as a local one.

The vault — pathways, never the destination

planned · last of the three

The third approved workstream, and the one with the sharpest boundary. Aoide builds the pathway; it is never the destination. It does not become a password manager — it brokers access to whichever one the host already trusts, from a daemon that runs as its own uid behind a socket that is its only door. The property it actually buys is stated plainly below, including the part it does not buy. Nothing in this section exists: no crate, no daemon, no verb.

dashed = planned, nothing exists · bronze = the gate that decides a release, and the path the value takes back · the two lanes are two uids, which is the whole architecture

planned — no code exists a uid boundary, drawn as the container it is what is written down, and what is never written

The one subtle decision is that the broker does not exec the command. The obvious shape — hand the broker an argv and let it run the process with the secret in its environment — is wrong for a reason that only shows up on the second reading: the broker runs as the vault uid, so the child would inherit the wrong working directory, the wrong environment, and the vault's own privileges. So the value is released to the client, which is already running as the agent's uid, and the client injects one environment variable, inherits stdio in both directions, execs, and passes the exit code back. That is honest rather than airtight, and the design says so: a same-uid agent holding a valid code could read the value it just obtained. The code is the gate, not the uid. What the design buys is exactly what it claims — without a code or a standing grant, an agent gets nothing at all; with one, it gets use.

The backends close the ownership trap structurally. Each named backend is one fetch-command template in the vault's own home — get = "pass show {name}", and stdout is the value. Because those processes run as the vault uid, the store behind them is owned by the vault uid: the GPG key, the session token, the age key belong to the account that brokers them and not to the account that asks. That is the difference between a rule written in a README and a rule the filesystem enforces. pass, gopass, bw, and sops are documentation presets, never code — Aoide learns no vendor.

Two ways a secret is authorised, and one enrolment per host. Per secret, requireTotp decides whether a code is demanded at all; the alternative is a standing grant for a named consumer, which is what an unattended service needs and what an interactive agent should not get. The codes are RFC 6238 over a hand-rolled HMAC-SHA1 — about a hundred and thirty lines whose test suite is the RFCs' own vectors — with a 30-second step, a one-step window either side, and single use per timestep enforced by a replay ledger, so a code read off a screen cannot be replayed by whatever else was watching. Enrolment is once per host: vault enroll prints the otpauth:// URI and its base32 always, and a QR code when qrencode happens to be there.

Mesh sharing comes last, and never touches agent-space. The A2A door runs as the operator's uid, so secrets do not ride it — not as a policy, but because the door has no access to the vault to begin with. Broker-to-broker gets its own loopback listener, tunneled exactly the way §V's federation edges are, vault uid speaking to vault uid, and it works only between hosts whose aoides are mutually registered and whose vaults have exchanged pairing keys. Two independent registrations, both required, both manual — the same enrolment discipline §V's L2 layer already runs on, applied one level deeper. A shared secret copies into the named host's vault as a replica; revocation pushes a delete; every step of it audits.

Two logs, and neither holds a value. The vault keeps its own append-only log inside its own home, which an agent uid cannot tamper with, and mirrors name-only events — the secret's name, the consumer, granted or denied, the command's argv[0] — into the one audit log every door in this report writes to. Values appear in neither, and the class carrying those events forbids the untrusted-data field outright. Rejected rather than deferred: injecting a secret into a running session as keystrokes. It would work, and it would write the value into the agent's own transcript, which is the exact failure this whole workstream exists to prevent.

The web app — planned, not built

a fourth client · and one real gap

Nothing in this section exists. No crate, no route, no file. It is described here because the shape of the ask is architecturally interesting: a browser surface that streams agent processes, drafts, and derivations; logs system output including the diff verbs' output; possibly carries the settings panel; and lets commands be quickfired at the system — "a similar job to what the CLI does, but even more extensive." The claim worth testing is that this is another client of the same server, exactly like the CLI and the desktop, needing no new protocol. Half of that holds and half of it does not, and the honest half is the more useful one.

dashed = planned, nothing exists · solid = live today · dotted = the reach a live piece actually has · the bronze box is the gap, not a design

live — the protocol substrate live — a running surface live — published document planned — no code exists

The command half of the claim holds. Quickfiring a command from a browser needs no new protocol and no new vocabulary. There is one registry, one dispatcher, one Outcome envelope, and the report's own §I rule applies unchanged: adding a door is a façade; adding a capability is a registry entry. A web command door would be a fourth façade over dispatch() — the same shape mcp serve already is, differing only in transport. On this plane the web app really is another client of the same server, and the settings panel is the easiest case of all: settings are commands, and every one of the 83 already describes itself through schema --json.

The streaming half does not, and that is the finding. Everything the ask names as a stream — agent processes as they move, drafts as they mint, derivations as they build, system and diff output as it is produced — has no transport today. Three things come close and each falls short for a different reason, verified in the tree:

So the honest statement is a split one. The web app is a door consumer on the command plane and a protocol extension on the state plane. The report has said all along that there are two planes and that the second one — song/stage/*.json plus the shellbridge socket — is versioned separately and is not registry-derived. This is the first ask that lands squarely on that second plane, and it exposes what has been true and unremarked: the state plane has a publication mechanism but no subscription mechanism. Every existing consumer is a local process that can watch a file.

What that implies, stated as a gap and not as a design. A web app needs a way to subscribe to state-document changes and to process output over a socket — which is a new contract with its own versioning, its own authentication story (the A2A door's bearer and origin rules are per-request and one-shot; a long-lived stream is a different problem), and its own back-pressure and truncation semantics for output that a session can produce faster than a browser consumes. Three pieces of the substrate are already in the right shape to build on and none of them is the thing: shellbridge is a single writer that could publish as well as write; aoided's default-deny class model is the correct authorisation shape; and the A2A door proves the house can hold an HTTP connection open and stream to it. Deciding which of those becomes the transport is the first real question, and it has not been asked yet.

Read this section as a gap, not a plan. Nothing above is designed, locked, or scheduled — there is no wiki page, no phase list, and no code. Its value is the negative result: the tidy answer ("just another client, no new protocol") is half right, and the half that is wrong is the half that would have been discovered late. If this is built, the streaming contract is the thing to design first, because the command façade is a small, well-understood piece of work and the transport is not.
