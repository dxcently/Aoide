What is Aoide

identity · and the problem it answers

Two things wear the name. Aoide is the orchestration core — a shell-only, headless-capable gateway between a machine and its agents: any agent with a shell is fully capable (no MCP required), and every terminal is a conductable, tracked session by default, so a central agent can speak into any other running session. AoideOS is the distribution built on that core: the NixOS flake that adds the Quickshell desktop and the song/livery ricing engine, painted by lyra. Aoide is the gateway; AoideOS is one venue it plays. You clone and run it, not install it.

The naming thesis in one line: architecture is frozen music — the Nix layer is the score, the running desktop is the performance, a rice is a song the system sings, and the host performing it is the venue.

The gateway framing is a test any file can fail (CONTRACTS.md §0): delete every .qml in the repo — is this capability still reachable from a terminal? No means it is in the wrong place. One body, several doors.

The problem it exists for: every agent harness is an island. Each owns a model loop but not the machine — capability arrives as a per-harness MCP list configured over and over, two agents in adjacent terminals cannot see or command each other, and nothing records what any of them did. Aoide puts one gateway between agents and the machine: every capability is one registry entry served through every door at once (argv, MCP, A2A, the daemon socket), and agent-commands-agent goes through one gated, audited path.

It wraps those loops rather than replacing them. aoide conduct -- <cmd> runs the harness you already use, model loop untouched, and puts the machine around it: a session id, a control socket, a place in the graph, an audit trail. On a NixOS venue that control is OS-level, because the same declaration that dresses a bar also sets the compositor, the system theme, and the generation you can roll back to.

The problem and the answer, side by side — the same three harnesses in both panels. The loops themselves are untouched; what changes is everything around them.

the gateway a conducted session a sight-line that does not exist

The differentiator is AoideOS. On top of the core sits lyra, the paint binary, whose bar, dock, conductor surfaces, and rice engine are all clients of the gateway — the desktop reads the same stage files and speaks the same commands an agent does. Together they give a declarative, composable, hot-swappable rice mechanic with first-class agent integration: a song is a committed score and the mode lock keeps the live system from drifting off it; songs, widgets, facets, and dendrites enter by existing at a path and leave without a trace; any committed song stages live with no rebuild. The desktop is one more thing the gateway serves.

The conductor tracks every terminal mechanically — hooks, PTY, transcripts — because observing is free; conversing costs tokens. Every chart below draws Quickshell at the edge rather than the centre, beginning with the next one.

Clients — what mounts, and what a new one costs

base map · region A

Region A is everything that mounts through a door, and the coding harnesses are the interesting case, because they are the ones you keep adding — Claude Code, kimi, pi, Codex, anything with a TTY or a CLI. The question: what does it cost to teach Aoide a harness it has never seen? There are five seams and all five are landed. The answer is one AgentProfile row and no Rust beyond it, because injection is gated by conduction — a pty aoide owns — and never by the harness inside it.

The profile table is the only per-harness registration point, and it is kept deliberately thin. protocol::agents holds one AgentProfile per harness: the hook-event map, the permission vocabulary, the sub-agent tool names, the payload normalizer, the model-context ceilings, the transcript locator and its extractors, the hook-settings spec, the launch/resume_args table, and permission_keys — the prompt hotkeys, verified by reading the live prompt on screen, or None, in which case the herald refuses to raise a summons rather than type a guess into someone's session. A field is added when live evidence earns it and not before: submit_key landed (b6cbd03) because a live kimi proved --submit's hard-coded \n typed a line without sending it, and it resolves from the target session's profile at delivery time, so a held entry approved later still speaks the right byte.

The other four seams are mechanism, not vocabulary. graph wrap --agent <name> -- <cmd> runs any CLI as a registered session; graph spawn is the detached headless form, re-execing conduct --headless into its own session with a log at state/sessions/<id>.log and registration proven by a live socket connect. The hook door inverts the other three: a harness session running inside a conducted terminal registers itself as a child by piping its own hook payload into aoide graph session hook — no new protocol, one registry command, the payload treated as data. And graph send plus the pending queue types into the pty and holds what is not authorised for a human. None of the four knows what harness it is driving.

One protocol, structurally. The CLI dispatcher, schema --json, the MCP tool list, and the A2A AgentCard all derive from one Registry in one crate, and nothing else in the tree enumerates commands, so there is nothing for ingress to drift apart from. Adding a door is a façade; adding a capability is a registry entry every door advertises at once.

The A2A door is complete and bidirectional (phases A–F all landed): AgentCard at /.well-known/agent-card.json, message/send (inject or spawn), tasks/get, SSE streaming, and the client side (a2a agent add/list/remove/send, folded into the session DAG as kind:"a2a" nodes). Peer federation rides the same door: another aoide registers as a peer (aoide peer add), aoide/graphSummary pulls its whole resolved session graph, and it folds in as a peer:* subtree — fresh within a 5-minute TTL, stale-but-present otherwise, never silently dropped. Federation is live-proven and two-way on two edges; §D1 records the runs.

Two planes, honestly. The command plane above is the one schema. There is a second, narrower contract — the state plane: song/stage/*.json documents the gateway publishes and clients watch, plus the shellbridge socket the painting client writes back through (CONTRACTS.md §4). It is versioned separately and is not registry-derived; the next section shows it as the gateway's notification stream.

Security model. The capability is admitted at rebuild time: enabling the door (aoide.a2a.enable, off by default, loopback by default) and setting aoide.a2a.spawnAgent are nix options, so turning A2A on goes through the normal rebuild gate, and a spawn only ever runs the configured command (the client supplies the prompt, never the argv). Per request, a non-loopback message/send auto-delivers only from a peer marked autogate; anything else queues pending for a human. With aoide.a2a.tokenFile set, one bearer-token predicate gates spawn and every read command, and loopback stops being a trust signal. Every outcome audits through Door::A2a into the one log every door writes. §D1 draws the whole trust model outside-in, with the open edges named.

What a harness must speak: argv and one envelope. The floor is a shell. aoide schema --json enumerates all 80 core commands with their args, flags, and gating (lyra schema --json lists its own 48); aoide guide is the prose companion. Every command answers in the same Outcome shape — status, command, message, gated, a changed list that is empty exactly when nothing happened (the idempotency signal), and an optional data payload (crates/protocol/src/output.rs). A harness that can run a subprocess and parse JSON is already a full client; the other doors add reach, never capability.

The hook attach point is not a fourth protocol. aoide hooks install claude|kimi|pi merges one entry into the harness's own settings file, and that entry runs aoide graph session hook — the CLI door, one registry command, the harness's hook payload arriving on stdin (crates/conduct/src/commands/hooks.rs). The payload is treated as data and never propagates as a command. §A takes the per-harness cost apart seam by seam, with the live matrix for the three harnesses actually tried.

And one command performs the attaching: aoide onboard. First boot is a flow, not a checklist — it registers the checkout as a graph project (reusing graph project add, the existing "register X as known" mechanism, rather than minting a marker file), links ~/song at the checkout's song/ without ever clobbering — an existing correct link is a no-op and anything else at that path is left alone with a note explaining how to hand it over — seeds the songbook preferences, then asks which harnesses to wire and runs the already-registered hooks install handler for each choice rather than reimplementing it. The ask is a real multi-select on a terminal, with two escapes for everything that is not one: --harness claude,kimi names the list outright, and --yes skips every prompt end to end and wires whatever it finds on PATH. Then it probes for lyra and hands the nix half to lyra onboard as a child process when the binary resolves — core never speaks nix itself — and closes by printing aoide guide, so the session that just installed Aoide ends holding the four-tier map. It is CLI-door only and checkout-only, both for the same reason the rest of this section keeps drawing: an interactive flow that spawns children has no meaning over MCP, A2A, or the daemon, and the clone is the thing being registered.

What gates it. The capability is admitted at rebuild time, through the nix options §B1's callout names. Per request, crates/server/src/a2a.rs resolves an origin and a bearer token, and then a second and separate gate inside graph::send decides delivery: an explicit --yes, the box-wide AOIDE_CONDUCT_AUTOGATE, or the sender being the target session's parent — an orchestrator freely commanding a child it spawned. Anything else queues in stage/pending.json for a human. That gate applies to every door, not just A2A; §D1 reads the whole ladder outside-in.

One honest limit on the wire door. The AgentCard advertises every implemented command as an A2A skill, but the door itself answers exactly five methods — message/send, tasks/get, aoide/graphSummary, and the two SSE methods (message/stream, tasks/resubscribe). Over the wire, A2A drives sessions: inject text into a known one, or spawn the configured agent. Arbitrary-command dispatch is the CLI door (argv) and the MCP door (stdio) — both local. A remote harness that wants to call rice lint directly does not have a door for it today; it drives a local session that does.

The seam that makes the paint test true. A harness attaches through the same doors the painting desktop uses, and the desktop's own return path is the shellbridge socket — one more client command. So an agent driving Aoide can reach the code that builds the OS and the code that builds the door it is speaking through. The limit is deliberate: authoring the change is ungated, admitting it is not. The rebuild stays user-gated, so an agent can write its own harness and cannot switch the system onto it alone.

D1.

The gates — the trust layers, outside-in

base map · region D

Security here is four layers, each answering a different question — who can reach the port, which peer is calling, what an unauthenticated caller may learn, and what may finally become a keystroke in a running session. They are read outside-in, the way a request arrives. L2, L3, and L4 run on the live system; L1 is policy — an invariant plus the transport this box borrows — exercised once, over an ssh reverse tunnel, by a real remote peer. What is deliberately absent is listed as plainly as what is present.

L1 is an invariant with a default, not a product choice. The rule is borrowed encrypted transport, never server-side TLS: the door is a hand-rolled HTTP server, so encryption and machine identity come from a layer beneath it. That is also why mTLS is rejected — client certificates would mean adopting a TLS stack the house has no other use for, or hand-rolling the hard half of a security protocol. The default binding is a tailnet, but the invariant names no vendor: ssh -L, headscale, vanilla WireGuard, or a TLS-terminating reverse proxy in front of loopback are equivalent substitutions, and swapping one for another changes nothing above this layer. What stays forbidden is the door listening on a raw LAN or WAN address by itself. The door is off by default and binds loopback, so L1 is drawn as policy.

L2 — enrolment is a ceremony, and that is the whole feature. Two instances become peers when a human runs aoide peer pair <target> on one box and aoide peer pair approve on the other. A commit-then-reveal handshake exchanges ed25519 public keys — only the first mover commits to its nonce before revealing it, so an on-path observer can never force one code onto both operators — and both ends derive the same six-digit code from both keys and both nonces. The peer lands in state/peers.json verified, with its own allows set, only after the operators have compared that code out of band and each confirmed on their own side. peer add --token-file and the door-wide bearer survive as legacy escapes for unpaired callers; the file is still an allowlist, and a caller that is not in it is a stranger. On that path each peer carries its own secret (root-owned, 0600) rather than sharing one, because a shared token cannot tell two peers apart — the same reason the ceremony's own answer is a key per instance.

The command surface is one verb taking one positional. A URL-shaped target dials directly; anything else is a hostname, resolved by a discovery sweep — a long one (~45s, wide enough to span an advertisement tick) rather than peer discover's few seconds — before the same ceremony core runs against the composed target. peer pair refuses a second positional outright instead of reading the first and dropping the rest, and approve/reject/watch match as subcommands ahead of a bare hostname of the same spelling, so a box actually named approve takes the explicit URL form. aoide peer pending lists what is parked — id, direction, state — and never the code: printing it in a listing either operator can glance at would collapse the out-of-band comparison into a copy exercise, so each side's peer pair approve re-derives it independently. That command takes its <id> only when more than one request is pending.

Discovery exists, and grants nothing. An a2a serve process may emit a one-line UDP broadcast advertisement — {v, name, host, user}, an instance name and the ssh hop its operator claims, never a credential, never a key or fingerprint, and never a door URL, since doors bind loopback — on the fixed port 8711, and advertising is off by default behind peer advertise and AOIDE_DISCOVERY_ADVERTISE. Hearing is on demand: aoide peer discover [--secs N] binds that port for a few seconds, validates every field of a line it did not author before printing it (house rule 4 — an advertisement off the network is untrusted data), dedupes into a bounded fold, and writes nothing at all. The claimed hop is a claim; the packet's source address is a fact — both are shown side by side precisely so they can be seen disagreeing, and anything that dials uses the observed one. A spoofed advertisement can misdirect a request; it cannot survive the mutual code comparison at the other end. Finding a machine is not joining it — the registry is still only ever written by a human completing a ceremony.

The popup is sugar, and it is opt-in. Every step drives from a plain terminal on both ends — the tty prompt, or --code NNN-NNN when it is scripted — and aoide peer pair watch --popup only puts the same gates at the seat. It runs as a user unit behind one nix flag, aoide.a2a.pairingPopup, default off on top of the desktop-facet gate the secrets watcher already carries, and it draws one dialog shape per direction. Inbound (the approver) collects the typed code through the six-boxes-plus-dash surface the secrets TOTP dialog already renders — lyra pair ask, zenity --entry where lyra does not resolve — through the identical gate the CLI holds, and never shows the code. Outbound (the requester) shows this instance's own locally-derived code and asks for a single Approve/Reject (lyra pair confirm, zenity --question), because retyping a code already on the screen proves nothing the click does not. Delete every .qml and the ceremony still completes at a terminal — CONTRACTS.md §0's test, drawn in miniature.

L3 — the door asks one question. token_authorized(token_configured, token_state) is the single predicate, and every arm asks it: the card GET, spawn (23f0a0e), and every read command — tasks/get, aoide/graphSummary, and both SSE methods (Phase G, 6d2f38e, tests in 46296eb). The gate is computed in the dispatcher before the read runs, so a real session id returns the error rather than its state, and the SSE pair is gated at the top of stream_task so an unauthenticated stream neither injects nor spawns. With no token configured — today's default — every path is pinned byte-identical by its own test.

Two edges this layer closed. An unauthenticated card GET gets a stripped card of exactly name, protocolVersion, and url (4e25fa3), picked off the full card so the two cannot drift; it stays 200 and keeps the a2a.agent-card audit label, because a GET returns a card rather than JSON-RPC. An unauthenticated message/send naming a context id gets a uniform synthetic submitted Task (cea9f1f) — one shape for a real id, a bogus id, and a non-conductable one, with no session lookup and no queue write; the spawn arm keeps its -32005. What remains open here is the rest of the #47 ladder: audit identity (F), the outbound bearer header (H), and auth-required-stays-local with the sudo-inject guard (K).

Why #50 shipped as a uniform response and not a hard gate. Refusing unauthenticated message/send outright would have broken the peers the design exists for. An enrolled peer authenticates with its own per-peer token, not the server-wide one, and aoide's outbound client sends no Authorization header today. A hard gate keyed on the server-wide token would have rejected correctly-enrolled peers while closing a leak the uniform answer closes just as completely: no existence oracle, no queue write from an unauthenticated caller. The outbound bearer header remains a tracked gap (#47 H).

The nuance that exemption carries, stated in the contract (851c92d): a caller matched as an autogated peer by its per-peer token, while a server-wide token is configured and it presents no valid bearer for that, is exempt from the uniform arm and reaches the real inject machinery — but effective_origin coerces it to Unknown, so it lands held pending rather than delivering. Fail-safe, and distinct from the synthetic arm, which never queues at all.

The far ends are §G's resident doors, so these edges run between always-on servers rather than open terminals.

A remote peer necessarily presents as loopback, and that is the design rather than a hole in it. Because L1 borrows encrypted transport instead of terminating TLS, a peer that is elsewhere arrives through a tunnel and reaches the door from 127.0.0.1, so the origin address carries no information at this layer. A valid per-peer token on a loopback-presenting connection delivers immediately, and the held-pending path is reached through per-peer autogate policy, never through a raw remote IP the door will never see.

The ceremony had to answer that in both directions. A loopback-only door is reachable through an ssh forward and nothing else, so the requester's own two POSTs ride the same via its peer record gets — the observed source address plus the advertisement's claimed login — rather than dialing an address that will never answer; the one exception is an advertisement with no ssh claim at all, where there is nothing to tunnel through and the dial stays direct. The approver faces the mirror image: every aoide/pairRequest from a tunneled requester arrives as loopback, with no observed address to derive anything from. So the request carries an optional selfVia claim — the requester's own ssh://[user@]host answer to how do you reach me back, its login defaulting to $USER and its host to the local outbound address routed toward the box being dialed, because a claimed OS hostname was tried first and resolved only through the router's DHCP-DNS, which is luck rather than a transport marker. It is self-asserted data of exactly the same trust class as the url field beside it: a marker, never a source of trust — trust stays in the public keys and the code comparison. With the claim present, peer pair approve's commit records url as http://127.0.0.1:<port>/ — loopback as seen from the far side, the port parsed off the requester's own advertised door and never off this box's — and via as the claim, in the same write as the pairing commit; absent, the commit is the shape it always had. The live mesh reads exactly that way: yomi-strix plus sakaki, chiyo, and osaka, each a verified peer at http://127.0.0.1:8710/ over its own ssh://<login>@<address> hop, carrying read and spawn.

L4 — and the honest admission underneath all of it. The same-user control socket is the real authority boundary: anything on the box running as the User can open it, so no amount of door gating changes what a local process may do. Hence AOIDE_SESSION_ID is documented as attribution, not security — a same-user environment variable any caller can set, so the provenance prefix built from it says who claims to be sending. Delivery is decided by a ladder that does not consult it: an explicit --yes, the box-wide AOIDE_CONDUCT_AUTOGATE, the sender being the target's parent, siblings under one live parent (on by default per the User's 2026-08-20 call), and otherwise the pending queue with a human's approve/deny. The prefix is single-line and CR/LF-sanitized so an injected payload cannot manufacture a second line, and a bare permission-verdict keystroke is never prefixed — prefixing the digit a TUI is waiting to read would corrupt the answer.

What is deliberately absent, and why. No hand-rolled crypto — the only comparison the door does on a secret is a length-independent byte loop, and everything stronger is delegated to whatever transport L1 borrows. No local name encryption — a session's petname, cwd, and title live in same-user files on a machine whose owner is the only user, so encrypting them would protect nothing from an attacker who has already lost the L4 boundary. No resident discovery listener — advertising is opt-in and hearing is on demand, so nothing holds a broadcast socket open between sweeps, and discovery never reaches the registry. Each is a decision with a reason, not a gap someone forgot.

D2.

The gates — the secrets broker

base map · region D

The third approved workstream, and the one with the sharpest boundary. Aoide builds the pathway; it is never the destination. It does not become a password manager — it brokers access to whichever one the host already trusts, from a daemon that runs as its own uid behind a socket that is its only door. The property it buys is stated plainly below, including the part it does not buy. The whole arc runs on both boxes: the crate, the daemon, the socket, TOTP, deployment under a dedicated uid, the built-in file backend and the write half, the per-secret gates, the code-entry popup at the seat, and age encryption at rest. Privileged operations on these hosts resolve their credential through the broker: a full system rebuild has run end to end that way, the value riding one process environment and appearing in no argv, no log, and no transcript. V5, mesh sharing, stays queued and gated on mutual host registration — the one dashed thing left.

The one subtle decision is that the broker does not exec the command. Handing the broker an argv would run the child under the secrets uid, with the wrong working directory, the wrong environment, and the broker's own privileges. So the value is released to the client, which already runs as the agent's uid, and the client injects one environment variable, inherits stdio both ways, execs, and passes the exit code back. That is honest rather than airtight, and the design says so: a same-uid agent holding a valid code could read the value it just obtained. The code is the gate, not the uid. Without a code or a standing grant, an agent gets nothing; with one, it gets use.

The backends close the ownership trap structurally. Each named backend is one fetch-command template in the broker's own home — get = "pass show {name}", and stdout is the value. Because those processes run as the broker uid, the store behind them is owned by the broker uid: the GPG key, the session token, the age key belong to the account that brokers them, not the account that asks. That is the difference between a rule written in a README and a rule the filesystem enforces. pass, gopass, bw, and sops are documentation presets, never code — Aoide learns no vendor. Two backends ship, a plain-file store and an age store, both expressed entirely through the same template mechanism, so neither is a special case in the code.

The socket is a published API, not secrets exec's private plumbing. The wire is JSON-lines over a unix socket, one request per line and one reply back, with exactly two ops: resolve reads a value and put writes one. A service speaks it directly — connect, write a line, read a line — with no model and no aoide binary in the loop; the commands are convenience wrappers over the same two ops for a human at a terminal. That is why CONTRACTS.md restates the wire for a reader who never opens the crate's Rust, and why its refusals carry machine-readable flags rather than prose a caller would string-match. put mirrors the release flow the other way: the value goes client-to-broker, read from stdin and never argv, never released back, and the broker — never the client — is the one allowed to know whether that name already holds a value, because a client-side existence check would be a resolve-shaped leak on an op that is not resolve.

Two ways a secret is authorised, and one enrolment per host. Per secret, requireTotp decides whether a code is demanded at all; the alternative is a standing grant for a named consumer, which is what an unattended service needs and what an interactive agent should not get. The codes are RFC 6238 over a hand-rolled HMAC-SHA1 — about a hundred and thirty lines whose test suite is the RFCs' own vectors — with a 30-second step, a one-step window either side, and single use per timestep enforced by a replay ledger, so a code read off a screen cannot be replayed by whatever else was watching. Enrolment is once per host: secrets enroll always prints the otpauth:// URI and its base32, and a QR code where qrencode exists.

Mesh sharing comes last, and never touches agent-space. The A2A door runs as the operator's uid, so secrets do not ride it — not as a policy, but because the door has no access to the broker at all. Broker-to-broker gets its own loopback listener, tunneled the way §D1's federation edges are, broker uid speaking to broker uid, and it works only between hosts whose aoides are mutually registered and whose secrets brokers have exchanged pairing keys. Two independent registrations, both required, both manual — §D1's L2 enrolment discipline applied one level deeper. A shared secret copies into the named host's store as a replica; revocation pushes a delete; every step audits.

Two logs, and neither holds a value. The broker keeps its own append-only log inside its own home, which an agent uid cannot tamper with, and mirrors name-only events — the secret's name, the consumer, granted or denied, the command's argv[0] — into the one audit log every door in this report writes to. Values appear in neither, and the class carrying those events forbids the untrusted-data field outright. Rejected rather than deferred: injecting a secret into a running session as keystrokes. It would work, and it would write the value into the agent's own transcript, which is the exact failure this whole workstream exists to prevent.

Deployment taught the design three lessons no sandbox could, each the same shape: a refusal that was correct and useless. Admin commands refuse a mismatched effective uid before they touch policy, root explicitly refused rather than bypassed, on a missing home as well as an existing one — a plain sudo had reowned the policy file and bricked the broker, and root creating the home is that failure one step earlier. Every denial names its cause and prints its fix, on the broker's own wire as well as the admin commands, because the agent-facing path is the one an operator actually hits. And put refuses to replace a stored value silently: a confirmation at a terminal, the --force spelling taught to a pipe, and an audit line distinguishing stored from replaced.

What is still owed. V5, the mesh phase, and the live proof of the door's broker-resolved bearer at the User's next switch. The mesh is the first consumer of the remote-reachability flag, which defaults to local-only precisely so that a non-local path must be granted per secret rather than inherited — written down before the phase that needs it, so nothing is retrofitted. One row in that table can fail in a way systemd is structurally blind to. After a transient monitor-output blip, Qt's wayland platform backend falls onto an internal placeholder screen and never reattaches to the real output. The process does not crash and does not exit — aoide-quickshell.service stays active while the desktop paints nothing, so Restart=on-failure has no failure to fire on. It was observed on 2026-08-28 and twice on 2026-08-29, the last occurrence leaving a bare desktop for about nine hours before a human noticed. The rebuild already reasserted the paint through the aoideRestartRice activation entry, but only ever on a rebuild; nothing watched for the same fault live.

No QML-side fix exists, and that is why the mechanism is external. Quickshell.screens is populated below QML by QGuiApplication's wayland platform plugin, so no in-process Quickshell.reload() and no onScreensChanged handler can reach the stuck state, let alone reset it — only a full process re-exec does. The watchdog is a command and a timer rather than a widget because that is the only layer at which the fix is available at all, and it lands on the right side of CONTRACTS.md §0's test for free: the capability is lyra quickshell healthcheck (crates/song/src/health.rs), still reachable from a terminal with every .qml in the tree deleted.

Two independent signals, and neither one acts alone. The unit's journal, scoped --since its own ActiveEnterTimestamp, must carry Qt's placeholder-screen line; and hyprctl layers -j must report zero aoide-namespaced layer surfaces system-wide at that moment. A failed hyprctl call reads as unconfirmed rather than as the stuck signal, so a broken probe never manufactures a restart. The ActiveEnterTimestamp scoping is the stateless debounce the design would otherwise have needed a state file for: a restart moves the timestamp forward, the line that triggered it falls out of view, and an already-recovered occurrence cannot re-trigger.

Two callers, one check. aoide-quickshell-healthcheck.timer runs it live, first sweep 20s into the session so the shell's own startup is never mistaken for a lockup, every ~15s after that. The rebuild runs the identical check: home.activation.aoideVerifyRice fires it five seconds after aoideRestartRice bounces the shell, so a nix switch confirms its own restart actually landed instead of reporting success over a bare desktop. The journal is the authoritative record, not the notification — dunst is configured skip_display and only forwards to lyra herald push, and the herald is drawn by the very shell that is broken, so the toast channel is the one surface guaranteed unavailable exactly while this fault is live.

Why the layer count is whole-system and never per-monitor. No PanelWindow in modules/facets/quickshell/qml/ binds to a screen, so the shell paints exactly one output — which means that on a multi-monitor host every other enabled monitor legitimately reports zero aoide- layers forever, by design. A per-monitor "is any enabled monitor empty" predicate would read a healthy two-monitor rig as stuck and restart the User's desktop out from under them. Summing across every monitor and every level instead makes the signal monitor-count-agnostic: zero total means the shell is painting nothing anywhere, which is the actual fault.

And why the ladder is a floor rather than a stop. The first design gave up permanently after three restarts and announced that through the notification path — so it stopped fixing a confirmed-broken desktop and told no one, because that path cannot render while the shell is stuck. The ladder replaces it: it slows against a flapping output without ever abandoning a desktop that could still come back, and the single notification at the floor says the output connection looks suspect rather than that anything has been given up on. Both points came out of independent review rather than the first draft — the same loop §III describes.

Why two binaries and not a feature flag. The conductor stays core, and that is the load-bearing call. base mapA · peer boxes → B · the A2A door → F · the durable plane

Presence is a live probe, not a cached guess, because the doors are resident. sakaki and osaka answer whenever the box is up, so host-up equals door-answering, and a freshness-decayed cache would model a problem that does not exist. aoide who probes every registered peer on every invocation, in parallel, with a short per-peer timeout, and there is no background pull timer. The peer cache is only the fallback: an unreachable box shows as unreachable with its last-known sessions labeled as of their fetch time rather than presented as current. A node reads online, unreachable, or never-pulled, and a remote session from a live reply is exactly as trustworthy as a local one.

who lives in conduct, and that settles a crate question rather than raising one. It projects the graph conduct already folds — a projection, not a new store — while driving live pulls through client's transport, which makes it the tenant of the one documented conduct → client edge the screen family opened and the split then vacated. The edge deliberately stays, with a Cargo comment saying why so nobody tidies it up between the two workstreams.

The resolver is the inverse of the display grammar §D1 renders on every human surface. Its one hard rule is that ambiguity is an error and never a first match — two sessions answering to zesty get an error listing both, because a resolver that guesses would type into the wrong agent's terminal, silently, exactly once before anyone noticed.

Cross-host sending adds nothing to the wire. A local target keeps the existing path — the same gate ladder, pending queue, provenance prefix, and audit line. A remote target resolves the query against that peer's graph to a remote session id and delivers it as an A2A message/send carrying that id as the contextId, which §B1's mapping table has called a SessionRecord since the door was built. The server side already routes it; the only client-side change is that the body builder stops hard-coding an absent context. Federation gains a command, not a protocol.

The conductor gains two panes, and re-derives nothing. A read-only roster renders rows by dispatching who --json through its injected dispatch function — the TUI never re-implements presence — grouped by peer and throttled to roughly one probe every fifteen seconds, because who does real network work and the UI ticks three times faster. A pending pane lists the approval queue with approve and deny on single keys, re-listing after every resolve because pending entries are addressed by position, and a compose line sends to a roster row through the same gated command a shell would use.

The inbox is the reversal worth recording. The pending queue plus the audit log were held to cover message history; headless residency changed the question, because an agent spawned an hour ago, or a box whose door took a delivery while nothing watched, has no way to find out what it missed. So a durable per-host inbox lands: every message persisted at both delivery seams, the local inject and the A2A door's, so local and remote arrivals land in one place; capped with oldest-drop on the herald ledger's precedent; read through plain inbox list / read / clear commands. Each message may carry an optional, opaque context field, stored and never interpreted — the seam Mneme will arrive through as the context and memory manager. v0 builds the seam and wires nothing to it, the discipline every other extension point here was built with.

Aoide is built by the loop it exists to run — the harness dogfooding itself. The diff in "diff agent loop" is different: the agent that reviews is never the agent that wrote. Review is a coaching step, not a verdict slot. An execute-tier agent wrote fugue's bar and herald (82ba5f9); a different agent of the same tier reviewed and found the new song had reintroduced two bugs sonata had already fixed. bar.qml bound implicitWidth off parent.width while WidgetSlot binds its own width off the loaded item's implicitWidth — a loop sonata defuses by binding width directly. The executor defended the first as an intentional simplification. The reviewer read sonata's fix, rejected the defence on the evidence, and coached the executor straight to the change — agent to agent, not a verdict routed through the orchestrator. That is 19ee9e4.

Re-derivation, not confirmation. A report is an assertion, and the loop exists to make someone else earn it independently. In 8c087ba the executor's central claim was unfalsifiable from the diff alone: sonata's new _widgets/ shelf changes nothing, because lib/walk.nix drops any /_ path and the built Quickshell config derivation stays byte-identical down to manifest.json and registry.json. The reviewer reproduced the derivation-identity gate in its own worktrees and compared the outputs itself. A reviewer that only checks whether its own suggestions were applied has stopped reviewing; the standing rule is that it grades is this wrong, never did my change regress it.

Vocabulary is a review surface too. 1d1465f renamed a widget record's instruments field to packages: the lexicon reserves instruments for what a venue sounds — which facets and dendrites a host enables — so the name meant the wrong thing and implied a song choosing its own facets, which CONTRACTS.md forbids. The follow-up (419628a) settled a second flag in the same area, where the guard's error message and the comment above it hedged between two words; an unsettled field name reads as an unsettled contract. Neither is a bug, and both are the kind of drift only a second reader catches.

The orchestrator's own test. It concretizes the ask, dispatches one role per unit, tracks, and lands by pathspec — never git add -A, never a stash, because other sessions are committing into this same index concurrently. It does not execute and it does not review. The dividing line for small work is one question: does this need a whole agent? A typo, a margin, a one-line tweak, a config bump — those stay with the orchestrator, because a cold agent would spend more re-deriving the context than the edit is worth.

Where the manual lags practice. docs/Aoide-Wiki/protocol/AOIDE-DEV.md §2.1 has the shape right — plan, execute, review; "review coaches the executor via SendMessage; it is not a bare pass/fail"; "the orchestrator dispatches and verifies, but does not implement or review" — and is stale in two places. It assigns review to the flagship tier, where practice has settled into a three-way split (standing as of 2026-08-21): the architect tier plans the loops and advises — architecture, phase plans, sequencing, never the baton; the design tier owns front-end design passes — report pages, web surfaces, widget treatments; and the execute tier both executes and reviews, a different agent each time, never the author's own context. It also puts the design advisor on call only when the User asks, which is not how the design passes run. And the requirement that the reviewer re-derive rather than accept the report is written down nowhere. This chart is the current truth; the manual is the item to amend.

The same loop, unbound from the harness

tiers · bindings · one spec

Plate III is the loop as it is run here, inside one harness that happens to have sub-agents. This is the same loop stated so it survives the harness: a tier is one fresh-context execution unit per role, and the mechanism providing that unit is a binding, not a rank. There are two bindings and neither is above the other. Everything on this plate is a spec, not a command — the primitives it composes are landed, and the loop lives as a wiki concept page (concepts/orchestration/Loop-Protocol.md), folding into the onboarding skill that is still queued.

solid accent = a fresh-context unit and the binding that is always available · bronze = the degraded rung and the judgment call · dashed here means deliberately absent, not pending

a role with its own context a binding — an optimization, not a rank the command that will never exist

Why define the tier by context rather than by mechanism. Stated as "use sub-agents", the loop is a claim about one harness and evaporates the moment the orchestrator is kimi, or pi, or something not written yet. Stated as one fresh context per role, it is a claim about the work: the reviewer must not inherit the executor's reasoning, and the executor must not inherit the planner's rationalizations. Both bindings satisfy that. Sub-agents are an optimization within the rung, and graph spawn is the floor, because it works on any conducted harness — which is what makes "the default is tiered" a rule rather than a per-harness declaration.

Three things force the session binding regardless of what the harness offers. A role that must run on a different harness or model than the orchestrator; a long-running executor that may need steering mid-flight; and any work the User should be able to watch. A spawned session has a log, a graph node, and a herald presence; an internal sub-agent has none of those and dies with the context that started it. Everything else is a per-brief judgment, on the User's standing guidance: long-running executors get sessions, short scoped work gets internal sub-agents.

Model-tiering is seasoning, not the tier. Planning on a flagship and executing on a mid-tier is worth doing where the harness offers models, but it is orthogonal — fresh-context-per-role is a real tier on a single-model harness. What is not optional is review integrity: the reviewer never shares the executor's context on any rung, a distinct model or harness is preferred whenever one is on offer, and every reviewer brief carries the grading discipline in words. Same-model rationalization is a briefing failure, not a spawning one, and this repo has the scar to prove which of the two it was.

And the loop deliberately never becomes a command. Every consequential step — ship or send back, coach or re-dispatch, kill an agent that has gone wide — is judgment, and a graph loop command would freeze it into Rust, where it goes stale on the first run that does not match the shape its author imagined and changing it costs a rebuild. So the roles, the gates, the send-back cycle, and the degradation ladder live as a specification — Loop-Protocol.md, written in aoide's own commands rather than any harness's tool vocabulary — while the code contributes what it already has: spawn, send, the pending queue, view, logs, transcripts.

The one profile change this earned — and it is done. The loop itself belongs nowhere in AgentProfile: no capability matrix, no tier map, no models list, because nothing would consume them. Exactly two edges of the substrate were still claude-shaped and both have landed — a per-profile submit_key consumed by graph send --submit and resolved at delivery time (b6cbd03), and kimi's permission_keys filled from a live screen rather than a guess (aedca0c). With the spec written down (4ab3fe6), #52 is closed. pi still gets no rung on the ladder until it completes a headless turn on the record.

The web app — planned, not built

a fourth client · and one real gap

Nothing in this section exists. No crate, no route, no file. The shape of the ask is what earns the space: a browser surface that streams agent processes, drafts, and derivations; logs system output including the diff commands'; possibly carries the settings panel; and lets commands be quickfired at the system — "a similar job to what the CLI does, but even more extensive." The claim worth testing is that this is another client of the same gateway, like the CLI and the desktop, needing no new protocol. Half of that holds and half does not, and the honest half is the more useful one.

base mapB · the web door (planned) · F · the state planes

The command half of the claim holds. Quickfiring a command from a browser needs no new protocol and no new vocabulary. There is one registry, one dispatcher, one Outcome envelope, and §B1's rule applies unchanged: adding a door is a façade; adding a capability is a registry entry. A web command door would be one more façade over dispatch(), the same shape mcp serve already is and differing only in transport. On this plane the web app really is another client of the same server, and the settings panel is the easiest case: settings are commands, and each already describes itself through schema --json.

The streaming half does not, and that is the finding. Everything the ask names as a stream — agent processes as they move, drafts as they mint, derivations as they build, system and diff output as it is produced — has no transport today. Three things come close and each falls short for a different reason, verified in the tree:

Every existing consumer is a local process — one that watches a file, or one that opens the daemon's unix socket.

What that implies, stated as a gap and not as a design. A web app needs a way to subscribe to state-document changes and to process output over a socket: a new contract with its own versioning, its own authentication story (the A2A door's bearer and origin rules are per-request and one-shot; a long-lived stream is a different problem), and its own back-pressure and truncation semantics for output a session can produce faster than a browser consumes. Three pieces of the substrate are the right shape to build on and none is the thing: shellbridge is a single writer that could publish as well as write; aoided's default-deny class model is the correct authorisation shape; and the A2A door proves the house can hold an HTTP connection open and stream to it. Deciding which becomes the transport is the first real question, and it has not been asked.

Read this section as a gap, not a plan. Nothing above is designed, locked, or scheduled — no wiki page, no phase list, no code. Its value is the negative result: the tidy answer ("just another client, no new protocol") is half right, and the wrong half is the one that would have been discovered late. If this is built, design the streaming contract first, because the command façade is a small, well-understood piece of work and the transport is not.
