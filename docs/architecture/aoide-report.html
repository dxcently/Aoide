What AoideOS is

general

Two things wear the name, and they are not the same. Aoide is the orchestration core — the shell-only, headless-capable bridge layer through which agents are freely orchestrated: any agent with a shell is fully capable (no MCP required), and every terminal is a conductable, tracked session by default, so a central agent can speak into any other running session. AoideOS is the distribution built on that core — the NixOS flake that additionally ships the Quickshell widget toolkit (bar, dock, gadgets, the DAG/conductor surfaces) and the song/notes ricing engine. Aoide is the engine; AoideOS is the desktop around it. You clone and run it, not install it.

The naming thesis in one line: architecture is frozen music — the Nix layer is the score, the running desktop is the performance, a rice is a song the system sings.

Every capability is reachable through one command registry via three doors — the CLI (a human or script types aoide <cmd>), the MCP façade (an agent reaches outward for tools), and the A2A door (a peer agent speaks to aoide over the wire). All three derive from the same schema, so they cannot drift.

I.

The declarative body

Nix · build-time

Everything the system is is declared here. nucleus holds the core services + the aoide.* option contract; dendrites are additive per-app integrations, each dormant until a host flips its .enable; facets are presentation surfaces. Nix builds the whole OS (closure, units, generations) — the running machine needs it. What decouples is the rice (widgets, songs, the aoide binary, song/stage JSON): plain files that'd run on another distro. The independence is the rice's, not the OS's.

III.

Three doors, one schema

nine crates, root now virtual

Still one dispatcher + one self-registering registry.rs behind every door (the Hermes pattern holds), but Phase 9 finished what Phase 6 stopped short of: the app shell itself moved out into crates/cli, and the workspace root became a bare virtual manifest — no [package], no src/. Domain handlers that used to sit in the root's commands/ now live with their domain (graph/hooks → conduct, rice/cover/design → song, usage → storage, a2a-serve/daemon/shellbridge → server, a2a-agent/melete-adapter → client); the root crate keeps only what's coupled to the assembled registry itself (meta, stubs, mcp serve's tool-count handler). protocol is still the sink everything depends on — registry/wire/output/policy, never the other direction — and server still can't reach cli's assembled registry (that'd be a cycle), so it's still injected in as a plain &Registry + dispatch-fn parameter at the two launch sites. A ninth, dev-only test-support crate now holds the shared test rig + env_lock.

The package restructure

one crate → nine

Pi-style: a monorepo of single-charter crates instead of one growing binary. protocol extracts first on purpose — it's the registry/wire/output contract every door and every other crate reads, so "one schema, N doors" stops being a convention and becomes something the compiler enforces. Everything above it (storage, conduct, client, server, song) depends only downward. Phase 9 went one step further than Phase 6 had: instead of leaving the root aoide package as the trunk, the app shell itself moved to crates/cli and the root Cargo.toml became a bare virtual workspace — nothing lives there but the manifest. Every phase lands as a reviewed, green-build unit — plan (Opus) → execute (Sonnet) → adversarial review (Fable) → land — and every external call site keeps compiling unchanged (the lib keeps the historical name aoide, so no use aoide::… caller moved).

Two phases remain deliberately deferred, not forgotten: management (host-ops — rebuild/switch/service control) has almost no real content to extract yet, by house policy (rebuild stays user-gated, no self-updaters); steward (a system-management agent with design-memory + self-audit) is blocked on a product decision that hasn't been made — is it LLM-driven itself, or a verb surface an external agent drives? evals is downstream of both and waits on them.

The A2A workstream

the third door

aoide's conductor was already a bespoke agent-driving client — PTY injection + transcript-scraping, the most fragile seam in the system. A2A (Agent2Agent, the Linux Foundation successor to the now-defunct ACP) gives that session graph a standard wire: external agents join aoide's tree, and aoide-run agents are callable from outside. It's the third door, and its discovery derives from the same registry as the other two.

Security model. The capability is admitted at rebuild time — enabling the door (aoide.a2a.enable) and setting aoide.a2a.spawnAgent are nix options, so turning on A2A goes through the normal rebuild gate. Per request is bounded (a spawn runs the configured agent, never a client-supplied command — the client supplies only the prompt) and audited (Door::A2a), loopback by default. Forwarded messages are data, never executed. There is no interactive per-request gate because a request/response can't block on your admission — the rebuild is the admission.
