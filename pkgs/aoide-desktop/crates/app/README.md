# aoide-desktop-app

The one window over the shell, and the `aoide-desktop` binary. The window's
state and calls live in `window.rs`; the Tauri glue (commands, the confirm,
the push channel) sits beside it. Nothing here starts a process itself: every
child goes through the shell's palette and exec.

## Layout

- `src/lib.rs`: `handler()` (the `generate_handler!` list), `main_window()` (the
  window's builder: its title, its origin guard, no devtools, no profile on
  disk) and `run()`, which checks the arguments, loads the pinned aoide once,
  and opens the window.
- `src/smoke.rs` (smoke builds only): the smoke directory, the record, the
  ready file and the scenario confirm.
- `src/window.rs`: `Window`. `palette`, `run`, `sessions`, `chat_open`,
  `chat_say`, `chat_close`, `asks_open`, `asks_close`, `ask_answer`. It holds the exec, the
  confirm, a busy flag, one reader thread per open chat, the asks reader, and
  the record of the asks it has pushed.
- `src/commands.rs`: the nine `#[tauri::command]` async functions, and under
  `smoke` the tenth, `smoke_note`. Each runs its body on a blocking thread.
- `src/confirm.rs`: the `Confirm` trait and the GTK dialog, shown on the main
  thread with plain text and Cancel as the default.
- `src/wire.rs`: the push shape a chat sends down its channel, tagged by
  `type`: `line` (one v1 chat line: `id`, `role`, `from`, `text`, `thinking`,
  `clipped`, `tool`, `ask`, `state`), `record` (any other JSON object a stream
  printed), `other` (text), `dropped` (a line past the cap) and `end`. The asks
  channel has its own tagged push, `AskPush`: `open` (an ask, as the shell's
  `View`), `gone` (`session`, `ask_id`), `other`, `dropped` and `end`.
- `build.rs`: tauri-build's manifest, `COMMANDS` (the ten names).
- `capabilities/main.json`: the nine `allow-*` permissions, granted to `main`.
- `capabilities/smoke.json`: `allow-smoke-note`, read by a smoke build only.
- `smoke/`: one JSON file per smoke scenario: `empty`, `chat`, `hostile` and `ask`.
- `tests/smoke.rs`: the headless harness, `required-features = ["smoke"]`.
- `permissions/autogenerated/`: tauri-build's output, committed. The workspace
  gate's `perms` step fails when it differs from a fresh build; the nix check
  does not run that compare.
- `tauri.conf.json`: the window's config. The CSP is `connect-src ipc:` only.
- `ui/` (the sibling `../../ui`): the page the window loads, `index.html`,
  `chat.js` and `chat.css`. See "The page".
- `tests/page.rs`: the scan of `ui/` for markup built from a string, and the
  page's title.

## Seams

- The palette is `palette::palette` over `palette::main_grants`. A command the
  palette does not list cannot be run.
- `run` checks with `palette::check` first. A verb of `act` or `none` asks the
  confirm before its child starts. A refused path or a confirm not answered yes
  starts no child.
- A chat's messages are spelled with `visible` and `spell` before they leave
  Rust.
- `sessions` keeps the harness each listed session runs. `chat_say` sends with
  `--harness <agent>` for that session, and with none for a shell. A session
  the window has not listed is listed once, and refused if it is still absent.
  A send that core refuses exits non-zero, and `chat_say` returns that as an
  error with core's message, never as a reply.
- `asks_open` follows core's `ask watch --json` through the shell's `asks::watch`
  and pushes each change on its channel, from one reader thread: one held child
  for the window. The window keeps each ask it pushes in a record keyed by
  session and ask id; an ask added again replaces its record, and a removal
  drops it only from the door that reported it. `asks_close` interrupts the child
  and reaps it before it returns, and the record is cleared when the reader ends.
- `ask_answer(session, ask_id, label, shown)` answers an ask the window pushed,
  through `aoide ask answer --expect <fingerprint>`, so core's gate and audit
  take it. The fingerprint and everything else the answer names come from the
  window's record of the ask; the page supplies the label, and for a yes above
  the native confirm's cap the digest of the call it showed. An approval's yes
  asks the confirm (button `Approve`) with the whole visible call; above the cap
  the confirm offers no yes, and the pane's digest must equal the digest of the
  dialog built from the record now. A no and a question's answer skip the
  confirm. Core's refusal is an error with core's message and the ask stays.
  One answer at a time can hold the confirm: a second is refused as busy.

## The page

The page is the chat view. The left pane lists the sessions `sessions` returns;
the right pane is the open chat. The first listed session opens when the page
loads, and a click on another closes the open chat and opens that one.

```
push (type)  ->  drawn as
line         user: a bubble on the right    agent: a bubble on the left
             thinking: a collapsed fold     tool: one collapsed row
             system: small and centred      `from`: a label in the bubble
             state: the status line, no bubble
             ask: a read-only card with its prompt and answers or options
record/other/dropped -> a small centred note
end          -> the status line says closed
```

The composer sends through `chat_say`: Enter sends, Shift+Enter is a newline. A
send core refuses is shown on the error line under the log, never as a bubble;
the person's own message comes back as a `user` line on the stream.

Every string reaches the DOM through `textContent`. The page builds no markup
from a string and runs no string as code; `tests/page.rs` fails for
`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`,
`Function`, a DOM event handler property or `setAttribute("on...")` in a
script, and for an on-attribute, an inline script or style in the markup. The
CSP (`tauri.conf.json`) allows only the page's own files, so the stylesheet is
a file and no element carries a `style` attribute.

## The smoke run

Under the `smoke` feature (off in every default and release build) the app
takes `--smoke <dir>`. It writes `<dir>/ready` once the page has loaded, and
one line per command to `<dir>/record.jsonl`: the command's name and its launch
number, never its text. Its confirm answers from `<dir>/scenario.json`, so no
input reaches the window's own dialogs. `smoke_note` appends a note as data.

The harness (`tests/smoke.rs`) runs each file under `smoke/` in its own
headless cage, with grim for the screenshot. A scenario file is
`{"confirm": true|false}` and, to serve a chat, three more fields: `follow`, a
file (relative to this crate) whose lines the fake aoide prints as the chat of
the one session it lists, `rows`, how many rows the page must draw, and
`shows`, texts the page's log must hold. The app, once the page has loaded,
notes `title <the window's title>` and runs a probe in the page that waits for
`rows` rows and `asks` ask cards, notes `dom {rows, asks, buttons, img, text}`
and, when the scenario names a `click`, clicks the answer button whose label
starts with it; the page carries no smoke code.
For a scenario with `follow` the harness also sets `FAKE_AOIDE_FOLLOW_FILE` and
`FAKE_AOIDE_SESSIONS` in cage's environment, which only the fake aoide reads.
The harness waits for that note before the screenshot, and fails the scenario
when the window is not titled `Aoide`, the rows differ, an `<img>` element
exists, or a `shows` text is missing. `empty` opens the window and does nothing
else; `ask` serves the ask fixture through the fake aoide's ask watch
(`asks_from`, with `FAKE_AOIDE_ASKS_FILE`, `FAKE_AOIDE_SESSIONS` and the
argv record `FAKE_AOIDE_RECORD` set), holds the page to its `asks` cards and
`buttons`, and, after the shot, to the one `ask answer` the click on a question
option must have run, exactly `answered`; `chat` serves the protocol fixture of the chat line; `hostile` serves
lines whose strings hold U+202E, an escape and an `<img onerror>`, and must
show them as the spelled text. The VM has no system GL driver directory (no
`/run/opengl-driver`), so the harness forwards exactly three variables from the
dev shell into cage's environment: `__EGL_VENDOR_LIBRARY_DIRS`,
`LIBGL_DRIVERS_PATH` and `GBM_BACKENDS_PATH`, which the `desktop` shell names
from its own mesa. It fails by name if one is unset. The harness also sets
`LIBGL_ALWAYS_SOFTWARE` and the `WEBKIT_DISABLE_*` variables for the smoke run.
After `ready` and the screenshot, the harness checks that each WebKitWebProcess
runs in a PID namespace of its own. A page process that shares the app's
namespace is unsandboxed (the fork in `vendor/wry` is what turns the sandbox
on), and the scenario fails by name.

## Extension points

- A window command: one `#[tauri::command]` in `src/commands.rs`, its name in
  `build.rs`'s `COMMANDS`, its entry in `generate_handler!` (`src/lib.rs`), and
  its `allow-*` in `capabilities/main.json`. The gate fails on any of the four
  missing.
- A smoke scenario: one JSON file under `smoke/`. The harness runs every file
  there and fails on one it cannot read.

The window's own run against a real aoide is the next lane's job.
